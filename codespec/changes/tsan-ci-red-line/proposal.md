| 字段 | 值 |
|:---|:---|
| 变更编号 | CHG-072 |
| 提出日期 | 2026-11-08 |
| 当前状态 | 已归档 |
| 关联需求 | 无 |
| 影响面 | `.github/workflows/ci.yml` 新增一条 ThreadSanitizer 定点作业；`tools/check/` 下新增判定脚本 `tsan_gate.sh`；`codespec/ARCHITECTURE.md`、`codespec/BUILD_OPTIONS.md`、`codespec/CODING_STANDARDS.md`、`codespec/specification/08-tooling.md` 的 CI 口径与验收纪律回写；`CHANGELOG.md` 记一条。**不新增 CMake 选项、不新增 CTest 测试、不改 `cmake/AuroraTests.cmake`、不改 `tools/check/declared_gates.txt`，公共 API 与产品代码零变化** |

## 动机

1. 两处线程竞态（定时器完成决议与监听口并发停机）修复后，只由本机一次性脚本守护，仓库里没有常驻判据。回归一旦发生，现有流水线不会有任何作业报红：AddressSanitizer 与 UndefinedBehaviorSanitizer 看不到竞态，纯行为计数在无锁状态下仍可能偶然全绿。

2. 全量插桩普查的红线不能直接照搬为常驻作业。普查口径下 461 例中 57 例失败、590 条报告，其中约 480 条来自第三方未插桩库内部；修复态下的全量零报告从未验证。把未验证的全量口径设为常驻门禁，等于用一个可能长期红的作业替代判据。

3. 定点门禁已有完整的三态实证：修复态四例全通过且竞态报告数为零；注入变异（撤掉完成决议的锁、把监听口句柄的原子交换拆成非原子两步）后四例全红、竞态报告数十条，报告命中本库源码；还原后回零。该组合同口径在仓库当前 HEAD 上复跑仍为零报告。把这一组已验证的最小集合固化为 CI 作业，是成本与信噪比都可接受的红线。

4. 项目没有 ThreadSanitizer 的 CMake 选项，`AURORA_ENABLE_ASAN` 与覆盖率开关都与之互斥。若为此新增一个开关，需要同步改动选项注册、平台互斥分支与构建选项文档，并把「开关注入」与「全局编译标志注入」的等价性重新验证一遍；而后者已在普查与定点门禁中逐字验证。红线应当复用已验证的注入口径，不引入新的代码路径。

5. 本提案的边界。不扩展竞态覆盖面（其余竞态面、Windows 平台专属翻译单元仍需各自的专项），不把定点集合扩成全量普查，不改变现有任何作业的触发与判据，不新增「现役一票否决」的 CTest 声明。

## 变更内容

1. 在 `.github/workflows/ci.yml` 的地址消毒作业之后新增单腿作业，沿用其骨架：检出、仓库可解析的排版器、编译缓存（独立分桶）、配置、构建、`ccache` 统计、测试。配置以全局 `CMAKE_C_FLAGS` / `CMAKE_CXX_FLAGS` / `CMAKE_*_FLAGS_RELEASE` / 链接器标志注入 `-fsanitize=thread`，关闭预编译头，并显式关闭地址消毒与覆盖率；C 与 C++ 两侧同时注入，避免第三方 C 库漏插桩。构建只取测试运行器目标，不构建全量工具与示例。

2. 新增判定脚本 `tsan_gate.sh`：清理上一轮报告残留，以 `ignore_noninstrumented_modules=1:log_path=<报告前缀>:history_size=7` 运行四个定点用例，随后同时检查 ctest 退出码与落盘报告正文中的竞态计数，任一非零即判失败。报告正文是唯一可信计数源——竞态是告警级，ctest 不回显通过用例的标准错误，只读测试日志会得到零报告假绿；判定也显式不使用会把红洗成绿的退出码开关。脚本不写绝对路径，报告目录可由运行环境覆盖，便于本机复现。

3. 作业只在拉取请求与主分支推送下运行，普通功能分支推送、每周定时与手动触发都不运行；原因是全量插桩冷构建约需二十分钟，与「每个分支推送都付一次」不成比例，而合入前的 PR 与合入后的主分支推送已经把红线放在了必经的两个位置。去重门控沿用流水线既有表达。

4. 定点作业不装配网络能力公共前缀（Inspector 服务器与 TLS provider）：该前缀是流水线其它作业的运行面约定，但本作业的目的是守住两处已修复竞态，实证基线正是在不含该前缀的配置下取得的；装配它会同时扩大插桩面、构建时长与第三方噪声来源，削弱判据的信噪比。

5. 判定逻辑具备独立可测载体，不内联在工作流脚本块里：本机可对同一脚本注入三种输入（零报告且测试通过、报告含竞态、测试退出码非零）验证它分别给出通过与失败，避免把「绿」当作门禁有效的证据。

## 验收判据

1. 在工作流的定点作业口径下，四个用例全部通过、竞态报告数为零、脚本输出通过；当前 HEAD 的本地复跑已给出 `CTEST_EXIT=0 RACE_COUNT=0` 的四例全绿读数。

2. 门禁可证伪：向报告目录注入一条含竞态告警的报告，或令 ctest 退出码非零，脚本必须判失败并以非零退出；两类注入分别转红，还原后回绿。绿不算证据，转红才算。

3. 注入产品代码级变异（撤掉完成决议的锁、把监听口句柄的原子交换拆开）时，定点四例必须红灯且竞态报告命中本库源码；还原后回零。该三态对照是这套用例集合能挡住回归的独立基准。

4. 工作流通过 `check_workflow_yaml` 与完整 YAML 解析；`check_change_proposals`、`check_codespec_xref`、`check_code_doc_sync`、`check_agents_size` 等静态门禁全绿；`check_declared_gates` 的声明数与 CTest 注册集合不变。

5. 本批不含 C/C++ 翻译单元改动，增量静态分析与排版检查的选择集为空；`aurora_api.json` 无差异。

## 回写落点

- `codespec/ARCHITECTURE.md`：§14.4 功能 job 计数由 14 组改为 15 组、作业清单补定点作业及其触发口径，并同步编译缓存分桶与「不装配网络能力公共前缀」的例外说明；§14.5 的本地验证表不动（本次新增的是 CI 作业而非本地目标平台），只把该节一处与 §14.4 不一致的旧作业数改为不含数字的引用。
- `codespec/BUILD_OPTIONS.md`：插桩与开关章节写明项目不提供线程消毒选项、常驻红线采用全局编译标志注入，以及地址消毒/覆盖率与之互斥的原因。
- `codespec/CODING_STANDARDS.md`：测试验收纪律补一条——竞态类缺陷不得只钉行为计数，须以消毒器报告正文与测试退出码的组合判定。
- `codespec/specification/08-tooling.md`：CI 作业口径表补定点作业一行，并写出报告落盘、残留清理与三类假绿陷阱的判据。
- `codespec/changes/tsan-ci-red-line/proposal.md`：本提案自身，状态为已归档。
