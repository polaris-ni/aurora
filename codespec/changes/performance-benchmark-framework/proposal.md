## 动机

1. **采集能力已经齐备，看护闭环却不存在。** 仓库有六个自研基准工具（`bench_render`、`bench_scroll`、`bench_theme`、`bench_win32_present`、`bench_idle_cpu`、`bench_gpu`）、`include/aurora/perf/` 下七个公共头、帧级分位数统计、确定性滚动采样自证与 `tools/check/perf_gates.json` 的十四项门槛。但没有任何入库的机器可读基线、没有跨提交比较、没有运行时性能持续集成作业。十四项门槛中只有 G-5 至 G-8 四项计数类由 `tests/unit/utest_scroll.cpp` 锁进持续集成；G-1 至 G-4 与 G-12 至 G-14 七项时间类只由 Windows 本机脚本按独立进程三次取最小值判定，G-9 至 G-11 三项帧阶段读数仅记录不判红、且只在打开插桩的构建下才有值。一次性能退化在合入时没有任何机制报红，读数只能靠人工保管。
2. **读数形态不可比较，权威口径已经漂移。** 除滚动基准外的工具只把 Markdown 表格写到标准输出；滚动基准虽有 `md` / `json` / `csv` 三视图，基线读数仍散落在阈值登记册的说明字段、工具规格表格与手工执行记录里，口径不同且无法被脚本消费。性能权威口径分散在一份自标「临时」的手工测试文档、`specification/08-tooling.md` 与阈值数据文件之间：`manual-test/17-perf.md` 头部称八个公共头而同文件表格与实际都只有七个，工具规格的基准清单漏列 `bench_gpu`，架构文档「所有组件默认关闭」与帧级组件恒开的事实不符；编译速度基线预设与运行时测量同名不同义。已退役场景的历史执行记录按既有约定只加注、不改写读数，也需要一处明确的收口说明。
3. **下游应用没有可调用的性能脚手架。** 渲染计数器是固定字段结构，没有自定义指标注册、订阅回调或上报钩子；`aurora_api.json` 里订阅、命名指标注册与追踪作用域类公共入口为零——已有的 `perf_snapshot`、逐原语耗时与各类 `to_json()` 只是库内读数导出，不构成下游可订阅的埋点契约。`AURORA_ENABLE_PROFILING` 默认取 `AUTO`，安装产物不导出该宏，因此拿到预编译 Release 库的应用开发者无法借助深度插桩宏监控自己的界面，只能改用库外计时手段，观测口径与库内无法对齐。
4. **共享持续集成环境的墙钟噪声不允许照搬静态阈值。** 跨运行器的处理器型号、频率漂移与邻居负载差异，足以让小幅真实退化淹没在噪声里，也足以让静态阈值频繁假红；三次独立进程取最小值是本机趋势对照，不是统计判定。可信判定必须以同机同次交错对照、足量重复、预先标定的噪声预算、并行指标的多重比较校正与按测试环境分桶为前提，并且把确定性计数类判据与统计性时间类判据分开处置。
5. **设计取舍与边界。** 现有采集层不重写，只补统一结果契约并向两侧长出能力；结构化编解码复用 `include/aurora/core/json.h` 与工具侧 `tools/include/json_file.h`，字段顺序沿用既有固定序列化实现，不另造第二套解析器或第二套读数口径。全体系维持零第三方依赖与静态库交付，统计判定自行实现，不链接外部基准库、遥测软件开发工具包或软件即服务平台。基线分两种载体各司其职：入库基线承担跨提交趋势追踪，同次双构建交错对照承担回归判定，二者互不替代、任一缺失即判数据缺失。时间类门槛采用分层看护而非拉取请求硬红；下游采用恒开订阅门面加编译期深度插桩的分层开销契约，零订阅者时零开销且不依赖安装期导出的宏。测试环境先覆盖 Windows 与无后端确定性场景两类，其余平台后续扩展；不做生产侧持续剖析、不做跨机器绝对数值比较、不承诺硬件级微架构计数器。

## 变更内容

1. **统一结果契约。** 定义单次基准运行的结构化结果文件并带契约版本号：运行元数据包含提交标识、构建指纹、编译器与构建类型、后端与测试环境规格、场景名、预热与丢弃规则、采样帧数、重复序号、交错种子与采样口径；数据段包含帧时间与分位数、渲染计数器、作用域聚合、自定义指标快照与可信度结论。时间读数统一单调钟与毫秒单位，分位数沿用 `FrameStats` 既有算法。字段命名与顺序沿用 `ScrollBenchHarness::Result`、`RenderCounters`、`TraceWriter` 已有的固定序列化实现，可与主流基准 JSON 映射但不引入其实现。六个基准工具全部落盘该文件并保留原有标准输出，滚动基准的 `md` / `json` / `csv` 三视图保持兼容；工具输出遵守既有日志与产品输出纪律。采样不可信须写入明确原因码；后端不可用、场景跳过或空读数时仍落盘结构化结果但标记跳过原因，判为数据缺失而非通过，不得静默产出看似可用的读数。
2. **入库基线与既有登记册处置。** 基线数据按测试环境规格、构建口径与场景分桶，附二进制与配置指纹，只允许由显式写入动作更新，普通测量只读。既有十四项门槛编号与语义原样迁入新契约，并按三类标注口径：G-1 至 G-4 与 G-12 至 G-14 七项时间类走 Release 关闭插桩，G-5 至 G-8 四项计数类走 Release 打开插桩并锁持续集成，G-9 至 G-11 三项帧阶段读数仅记录不判红、缺少插桩构建时记不可用。`tools/check/perf_gates.json` 继续作为阈值唯一登记册，本机判定脚本与 `tests/unit/utest_scroll.cpp` 按编号读取的既有路径不动，迁移不得复制阈值或改写读取方；本机三次取最小值保留为趋势对照入口，不作为统计判定来源。基线仓库与登记册是两份不同的数据，前者记读数、后者记阈值。
3. **统计比较载体。** 新增零第三方依赖的判定载体，至少实现：同一份代码两臂同码对照以标定变异系数与噪声预算；每臂有效重复不少于九次以支撑双样本秩检验；交错顺序由显式种子决定并写进结果元数据，未给种子拒绝执行；相对变化须同时超过噪声预算与指标族最小可检出变化，再经双样本秩检验与多重比较校正给出显著性；输出「通过 / 回归 / 噪声不足 / 数据缺失」四种独立结论的机器可读判定。同次双构建交错对照用于回归判定，入库基线用于趋势追踪，任一侧缺失时结论为数据缺失，不回退到静态阈值。禁止用单次绝对值或同次多进程取最小值代替统计判定；基线缺失、读数缺失、测试环境不匹配一律判失败而非跳过。
4. **分层持续看护编排。** 计数类与确定性指标继续由既有单元测试硬红守护，注册集合不变。新增独立夜间持续基准作业：同一运行器内构建基线侧与变更侧两套产物，交错采样后由比较载体产出报告，上传机器可读结果与作业摘要；时间类超阈值只产生告警，不改变拉取请求状态，也不改变既有持续集成作业的通过或失败语义。噪声预算由两臂同码对照稳定后，再由显式动作决定哪些指标升级为硬红。作业脚本不进持续集成测试注册、不进 `tools/check/declared_gates.txt` 现役声明清单；工作流块标量内不写注释行，环境变量值经标准解析器读入并断言。复用仓库既有的注入变异自证与编译速度基线产物形态，不新造第二套报告协议。
5. **下游脚手架的分层开销契约。** 在 `include/aurora/perf/` 新增订阅门面公共头：进程级单例的多订阅者帧完成回调按单线程界面线程帧末批量投递，自定义命名指标按名称唯一注册与注销、重名报明确错误而非覆盖，带句柄的作用域计时入口，以及结构化快照导出入口。投递前取订阅快照，回调期间注销只对下一批生效，句柄失效后可安全重复注销；单帧批量有固定上限，慢订阅者超限即丢弃本批并暴露可查询的丢弃计数，不阻塞帧、不改帧语义。零订阅者时不挂底层采集、不分配、不读时钟、不写日志与文件，作用域计时立即返回空句柄；Release 构建下恒可用，且不依赖 `AURORA_ENABLE_PROFILING`（`AUTO` 不随安装导出）。深度作用域插桩仍由该开关编译期归零，独立 `AURORA_ENABLE_TRACING` 打开时隐含强制开启插桩的既有关系不变；二者开销边界在构建选项文档写明。导出只产本库结构化数据与既有 Chrome Trace 时间线兼容格式，不链接任何遥测或剖析软件开发工具包。
6. **公共 API 同步与测试。** `aurora_api.json` 由生成器从控件注册表反射生成，不扫描性能公共头的自由函数，因此新增脚手架条目须扩展生成器登记来源或 `codespec/debug_api.toml`，再刷新对应目标，不能只靠重跑生成；伞头本体与 `tools/check/umbrella_manifest.txt` 的三分类及全头覆盖检查同步，按 `AGENTS.md` §3.1 的公共 API 门禁集合逐项过检，并遵守一源文件对应一个单元测试与一个示例的既有纪律。新增单元测试覆盖多订阅者互不覆盖、注销后不再回调、回调期间注销与重复注销不悬空、命名指标重名与序列化往返、慢订阅背压计数、以及以预编译 Release 库链接的下游消费示例。`AURORA_ENABLE_PROFILING` 的 `AUTO` / `ON` / `OFF` 三态与独立追踪开关组合都纳入构建与测试覆盖。
7. **需求锚点与文档收口。** 在 `SPECIFICATIONS.md` 特性表新增一条 `PERF` 类量化运行时性能需求，按该文编号规则取三位数字尾，规格落点须为可达链接，帧预算与分位数口径引用既有帧级实现与 G-1 至 G-4 而不承诺跨机器绝对数值；同步特性清单标题计数与文档地图。把性能测量、门槛分工与基线比较的权威口径收口到工具规格，修正架构文档「所有组件默认关闭」与恒开组件的冲突、手工测试文档八个公共头与工具规格漏列 `bench_gpu` 两处漂移；已退役场景的历史执行记录按既有约定只加注、不改写读数。指南补统一结果文件的运行配方、基线写入动作与下游脚手架最小示例；根目录变更日志记一条。
8. **明确不做的事。** 不改既有公共符号的可见性、不改现役门禁声明集合与全量持续集成矩阵、不改后端矩阵与分层边界、不改阈值登记册的既有读取方与本机判定脚本的判定语义、不引入第三方库与对外网络上报、不把编译速度基线改名为运行时测量、不新增生产环境剖析组件、不在未标定噪声预算前把时间类门槛升为硬红。

## 验收判据

1. **库内看护：** 六个基准工具在各自可用测试环境下全部产出结构化结果文件，契约版本与字段齐备且可被独立脚本解析；采样不可信或字段缺失判失败而非静默通过；后端不可用或场景跳过的工具仍产出带跳过原因码的结果文件并判数据缺失、不计为通过；原标准输出每项读数与结构化文件逐项一致，以此作为契约正确性的独立基准；结果文件可由既有 JSON 解析器往返读回。
2. **库内看护：** 基线按测试环境规格分桶，跨桶读数不参与比较；同一基线重复测量不被隐式改写，显式写入动作有可核的产物差异；对基线文件注入篡改（改阈值、改指纹、删条目）与缺失两类变异，判定载体须分别转红，还原后回绿；阈值登记册的两个既有读取方在迁移前后断言结果一致。
3. **库内看护：** 比较载体可证伪——注入一次确定性退化（强制整树重排或加倍绘制路径）须判回归；同一份代码作为两臂重复三次，相对变化落在噪声预算内且不判回归；每臂有效重复不足九次须判「噪声不足」而非通过；同一显式种子重放须得到同一交错顺序与同一结论；并行指标族的多重比较校正有单元测试覆盖，注入单指标轻微扰动不得因并行检验数量增加而被误判回归。绿不算证据，注入变异转红才算。
4. **库内看护：** 夜间作业在同一运行器内构建并交错执行基线侧与变更侧，上传机器可读报告与作业摘要；时间类超阈值只产生告警、拉取请求状态与既有作业通过失败语义不变；计数类单元测试硬红不变；工作流可被标准解析器完整读入且块标量内环境变量值不含注释字符；现役门禁声明数与注册集合、持续集成测试注册集合均无差异。
5. **库内看护：** Windows 与无后端确定性场景两类测试环境都产出结果且各自分桶，跨桶读数不参与任何比较；平台不支持的基准只产出带跳过原因的分桶读数、不谎报有效采样；报告如实标注测试环境，其余平台不谎报已覆盖；入库基线与同次双构建对照分别出趋势与回归两类结论，任一侧缺失判数据缺失而非回退静态阈值。
6. **下游脚手架：** 零订阅者在 Release 下的开销以可确定性区分的量度量——底层钩子注册数、堆分配次数、时钟读取次数与产物字节数在零订阅时恒为零；把订阅门面改为无条件采集的变异须使这些计数非零并令判据转红，还原后回绿；成对基准中位数差只作为辅助上界，不得单独充当绿判据。
7. **下游脚手架：** 两个订阅者收到同一批帧读数且互不覆盖；注销后不再回调；回调期间注销、句柄失效与重复注销不悬空；命名指标重名报明确错误、读写与序列化往返一致；慢订阅者超限只增加丢弃计数、不拖慢帧且不改帧语义；以预编译 Release 库链接的下游示例无需重编库即可读到自定义指标。
8. **下游脚手架：** `AUTO` / `ON` / `OFF` 三态与独立追踪开关的组合下公共头、配套单元测试与示例全部通过；`AUTO` 不导出宏的安装产物仍能编译并运行下游示例；零订阅时作用域计时不构造对象、不读时钟。
9. **全仓一致性：** `aurora_api.json` 的脚手架条目来自可扩展的登记来源而非手工改写入库文件；伞头清单、公共头分类清单与全头覆盖、单元测试与示例注册同步；API 结构、命名、文档注释、伞头、预算、分层边界等静态门禁全绿；改动文件的增量静态分析与格式检查无新增告警。
10. **全仓一致性：** 提案契约、条目编号连续性、反引号路径存在性、文档交叉引用与代码文档同步自查通过；特性表新增需求行有可达规格落点且标题计数、文档地图同步；性能文档口径无漂移、历史执行记录未被改写；根目录变更日志记一条；全仓无新增第三方依赖与对外网络上报。

## 回写落点
