## 动机

1. **剪贴板与系统拖放是同一体系的两半，两处立骨犯的是同一个病。** 剪贴板富格式立骨（CHG-013）与系统拖放事件族立骨（CHG-012）共享 `include/aurora/app/mime_types.h` 这一 MIME 词汇表单一真源——两条通道本应是同一套词汇的两个出口，剪贴板需求行本身就写着「MIME 词汇与空口径同系统拖放一致」。但两份立骨都把**平台语义误当接线细节**留给了接线程：惰性提供、所有权通知、变更监听、动作翻译、会话回调这些不是「后端接上就自动有」的东西，接线程做完了它们也无处安放。本提案把两条通道缺的契约**一次补齐**，避免同一套词汇在两条路径上各长一次。关联需求取其文本明确横跨两条通道的那一条（剪贴板富格式），系统级拖放需求 `SPEC.FEAT.APP.SYSTEM-DRAG-DROP.001` 同为本提案覆盖对象。
2. **剪贴板写入一律立即落盘，复制一张大图必须先把它编码完。** `Clipboard::set_text` / `set_image` / `set_payload` / `set_files` / `set_html` 全是「给字节 → 立刻写进系统剪贴板」（Windows 上为 `EmptyClipboard` + `SetClipboardData`）。延迟渲染是全平台标配：Win32 用 `SetClipboardData(format, NULL)` 声明「我能给这个格式」，数据在 `WM_RENDERFORMAT` 到来时才生成；macOS `NSPasteboard` 的 promise 与 `NSFilePromiseProvider` 同款；GTK4 的 `GdkContentProvider` 本就是惰性回调；Qt 靠子类覆写 `QMimeData::retrieveData()` 按需生成。缺了它，应用复制一张大位图就得当场完成 PNG 编码，哪怕用户根本不会粘贴。
3. **没有所有权通知，惰性提供就无法安全落地。** 延迟渲染的数据何时可以释放，全靠所有权通知：Win32 `WM_DESTROYCLIPBOARD`、X11 selection owner 被夺、Wayland `wl_data_device` selection 事件、macOS `NSPasteboard` 所有权变更。本库当前**两者皆无**，而这两项**成对**：只加惰性提供不加所有权通知，应用不知道手里的字节该不该继续留着；只加所有权通知没有惰性提供，通知也就没有可释放的对象。
4. **应用无法感知剪贴板内容变化。** 全平台都有变更监听：Win32 `AddClipboardFormatListener`（`WM_CLIPBOARDUPDATE`）、Qt `QClipboard::dataChanged`、GTK `GdkClipboard::changed`、macOS `NSPasteboard` changeCount 轮询。本库一个都没有，直接后果是「粘贴」按钮无法随剪贴板内容启用或禁用。
5. **缺程序化清空。** `clear()` 在 `QClipboard::clear()`、`gdk_clipboard_set_content(NULL)`、Win32 `EmptyClipboard()`、macOS `clearContents()` 上都是标配。当前应用只能写一个非空值把内容顶掉，在隐私场景（退出时清掉刚复制的凭据）下既笨拙又不可靠。
6. **拖入侧载荷读取同步阻塞，单线程 UI 下必然卡帧（两条通道里最致命的一项）。** `DragPayload::bytes()` 直接返回 `Result<std::vector<std::uint8_t>>`，`files()` / `text()` / `image()` 全建立在它之上。拖放载荷的真实来源只有两类：要么后端已一次性读入内存，要么仍挂在 OS 会话上按需拉取（Win32 `IDataObject::GetData` 的延迟渲染、Wayland `wl_data_offer.receive`）。后者意味着一次 `Drop` 态读取可能触发跨进程 IO——本库是**单线程 UI + 帧循环**，`Drop` 事件在帧上派发，同步读完一个大文件即是一帧的整段停顿。拖出侧反而不缺：`DragOffer::provide` 本就是按需回调，惰性提供已成立；**缺口严格在拖入侧的只读句柄上**。
7. **跨进程拖拽没有源侧视觉。** 全仓检索 `drag_icon` / `set_drag_icon` / `drag_pixmap` 零命中。Qt `QDrag::setPixmap`、GTK4 `GtkDragSource::set_icon`、wxWidgets `wxDropSource::SetIcon`、WPF `GiveFeedback` 都是标配：跨进程拖拽时跟随光标的影像由**源应用提供给 OS**、OS 合成显示，本库不参与绘制。缺了它，四态做得再全，用户看到的也只是「拖了个看不见的东西」。
8. **Move 动作的删除与回滚语义悬空。** `DragAction::Move` 的语义被写为「源在放置后移除其数据」，但契约里没有任何一处表达「目标确实接收成功了」与「源删不动时怎么办」。业界有明确协议：源只有在 drop 以 `Move` 成功结束后才删原数据；目标侧接收失败要能被源感知。当前 `on_system_drag_end(DragAction)` 只告知最终动作，既无成功确认也无回滚入口——`Move` 因此是一个**无法安全实现**的动作。
9. **源侧会话回调只有「结束」，没有「开始 / 取消 / 逐点反馈」，且其根因是执行模型未定义。** GTK4 有 `drag-begin` / `drag-end` / `cancel`，WPF 有 `GiveFeedback` 与 `QueryContinueDrag`（后者承载 Esc 取消与光标逐点切换）。本库只有 `on_system_drag_end`，且把「被取消」「被拒绝」「建立失败」三种截然不同的结局**折叠成同一个 `DragAction::None`**——控件无法区分「用户按了 Esc」与「目标不接受」，也就无法给出正确反馈。
   - **更硬的事实**：`system_drag::begin(const DragOffer &)` 当前是**同步返回** `Result<DragAction>`（inert 后端立即回 `DragAction::Copy`，无后端立即报错），真实后端接线后必然是「阻塞直到会话结束」的形态（Win32 `DoDragDrop`、Qt `QDrag::exec()` 皆如此）。而本库是**单线程 UI + 帧循环**——若 `begin()` 阻塞期间不泵帧循环，那么「会话已建立」「被 Esc 取消」这类回调**根本无从派发**。也就是说：补齐 begin / cancel 不是一个「加两个虚函数」的问题，而是**先要定死会话的执行模型**。本提案据此改用**事件驱动**（GTK4 口径）：`begin()` 发起即返回、不再阻塞，会话结果经回调投递。这是本提案唯一的破坏性改动，其余各条要么独立于它、要么以它为前提。
10. **修饰键到动作的翻译没有数据源。** `Event` 基类只有 `is_handled`，不含修饰键；`SystemDropEvent` 因此拿不到「用户按下 Ctrl 还是 Shift」。修饰键→动作的映射（Ctrl = Copy、Shift = Move）在系统拖放中是全框架标配，而本库当前既没有修饰键字段，也没有约定**由谁**把修饰键翻成 `proposed`。这比「归属未定义」更硬：**数据都没有**，后端想填也填不进去。
11. **长目标与滚动目标的自动滚边在系统拖入侧缺失。** `include/aurora/widget/reorderable_list.h` 为**进程内**重排内建了近边缘 auto-scroll（`auto_scroll_threshold`），但跨进程拖入侧全仓零命中，也无契约：把文件拖到一个长列表底部时，用户无法在不放下数据的前提下滚动目标。
12. **错误码缺位，读取失败与降级反馈无处安放。** 两条通道合计只有五枚既有 slug（剪贴板三枚、拖放两枚）。其中拖放侧的 `DragPayload::bytes()` 与 `image()` 已返回 `Result`，文档口径写明「会话失效等读取失败为结构化 `Error`」——**失败通路是有的，缺的是专属错误码**：文件被占用、源进程中途取消、`GetData` 失败、图像解码失败目前只能映射到语义不合的既有 slug 上。同时「读取失败后光标与 UI 状态怎么反馈」从未定义。
13. **两条明确排除项，理由留痕以免后人重复评估。**
    - **异步读取**：剪贴板读取时机由应用自己选（用户按键触发），不在帧循环关键路径上；拖放则是 OS 在帧上把事件推给你、必须当场响应——两条通道的理由不同，但结论一致：**剪贴板不引入异步读取通道**（业界主流靠延迟渲染把代价后移，而非异步 IO），**拖放保留异步通道的存在性**（Wayland 协议层没有同步读这回事，后端接线时不得不异步），形态定为**回调 + 帧循环排空兑现**（见变更内容第 2 条，与拖出会话的事件驱动是同一套「异步结果在帧内排空」的哲学）。
    - **统一数据对象**：Qt 的 `QMimeData` 同时服务 `QClipboard` 与 `QDrag`，GTK4 的 `GdkContentProvider` 同时服务剪贴板与 `GtkDragSource`，macOS 的 `NSPasteboard` 与 dragging pasteboard 是同一套——**业界确实普遍用一套数据对象服务两条通道**。本库当前是两套：`Clipboard` 是静态门面，`DragPayload` / `DragOffer` 是拖放侧的实例句柄与要约，两边只共享 MIME 常量。处理是**让两侧要约同构而不合并**：`ClipboardOffer` 与 `DragOffer` 取相同的字段形态、共享同一张常量表，应用可自行把同一个 `provide` 回调交给两条通道；但不引入跨 `app/` 与 `event/` 的统一数据对象——那会推翻 CHG-013 定下的「同址扩充、不新开门面」定位，且 `event/` 不依赖 `app/` 的分层约束使合并无从落地。

## 变更内容

### 两条通道共用的数据面

1. **惰性提供要约同构。** `include/aurora/app/clipboard.h` 同址新增值类型 `ClipboardOffer`：`formats`（MIME 清单，顺序即优先级）与 `provide`（按 MIME 取字节的回调，返回 `Result<std::vector<std::uint8_t>>`），字段形态与拖出侧 `DragOffer` 同构，MIME 取值一律来自 `include/aurora/app/mime_types.h`。`include/aurora/app/mime_types.h` 本身不新增常量——它已是两条通道的共同真源，本提案只让新的惰性面也走它。
2. **拖入侧非阻塞读取：定为回调形态 + 帧循环排空兑现。** 入口取 `read_async(const std::string &mime, std::function<void(Result<std::vector<std::uint8_t>>)> cb)`，`SystemDropEvent` 上的四个便利读取同步扩出非阻塞版本。四条契约边界 + 一条实现约束：
   - **边界一**：`DragPayload` 增非阻塞读取入口，读取期间**不得阻塞帧循环**；`Drop` 态读取大载荷时帧循环继续推进。**入口必须同步覆盖事件层**：`SystemDropEvent` 现有 `files()` / `text()` / `image()` / `bytes(mime)` 四个便利读取全部委托 `DragPayload`，若只扩 `DragPayload`，控件拿到事件后**仍只有同步一条路**——事件层须有对应的非阻塞便利读取（命名取同步名 + `_async` 后缀：`files_async(cb)` / `text_async(cb)` / `image_async(cb)` / `bytes_async(mime, cb)`，回调签名与 `DragPayload::read_async` 一致），否则这一项等于没补。
   - **边界二**：现有同步入口 `bytes()` / `files()` / `text()` / `image()` **全部保留、语义不变**，用于小载荷、无头测试与同步后端；新增入口是**并列通道**而非替换。
   - **边界三**：空口径与失败口径沿用既有定义——格式不存在 = `Ok` 空值（空内容不是失败），读取动作本身失败 = 结构化 `Error`；与 `Clipboard` 同口径。
   - **边界四**：非 `Drop` 态访问载荷按空口径返回、不崩溃；在途读取在会话结束（`Leave` 未落放 / 会话取消）时按既定兑现规则收口，不得悬挂。
   - **边界五（实现约束，非可选项）**：`DragPayload` 现有读取方法**全为 `const`**（`bytes() const` 等），其拷贝与移动赋值均被 `= delete`，而 `SystemDropEvent::payload` 是 `std::shared_ptr<const DragPayload>`。非阻塞读取必然要在句柄内登记在途项，故实现须落在 `mutable` 内部状态上；且须定义**同一 const 句柄被并发读取**的语义——多个持有者共享同一 `shared_ptr` 时，在途项按「每次读取调用各自独立登记、各自兑现一次」处理，不共享结果、不互相取消。
   - **兑现模型（与第 8 条同一套哲学）**：在途项由**帧循环排空**驱动兑现，回调在帧内排空、**不在平台消息泵内同步回调**——`Application::step_frame()` 的既有注释已把这条定为通则（「回调可能重建页面 / 触发重排，在消息泵内重入会把布局与绘制切到半途的状态」）。排空点在 `step_frame()` 内与 `NotificationCenter::pump_events()` 并列。`system_drag` 增 `pump_reads()` 入口（与 `NotificationCenter::pump_events()` 同款返回 `void`；无在途项时近零开销）；**宿主不排空 ⇒ 回调不到**（沿用 `NotificationCenter` 的「不会虚假成功」口径，不谎报）。
   - **兜底与超时**：在途项一律**兜底兑现**——会话收口（结束 / 取消）时就地兑现未决读取，失败或空口径按边界三给出；源侧迟迟不给数据时按**墙钟超时**兑现 `system-drag-read-failed`（沿用该 slug 的 `retryable = true` 口径，不新增超时专用码）。回调**只被调用一次**，调用后即摘除在途项。
   - **不返回读取句柄**：会话级收口已覆盖全部取消需求，`Leave` / 会话取消必然收口所有在途项，故单个读取的独立取消没有价值——与 `NotificationCenter::notify()` 无句柄同款，保持 API 面最小。
   - **为什么不复用 `Task` / 协程（选型留痕，免后人重评）**：`include/aurora/state/async.h` 的 `Task<T>` 与 `include/aurora/state/coroutine.h` 的 `CoroTask` 都是为「**后台执行**」设计的——`async()` 启动后台线程跑 `fn`，`CoAwaitable::await_suspend` 交线程池执行。而拖放读取的等待**不在后台线程**：Wayland 下是 `wl_data_offer.receive(mime, fd)` 之后由源进程往 fd 写、靠**主线程事件循环**驱动收齐，丢后台线程会与 display 的事件循环竞争。此外 `Drop` 回调不是协程上下文，控件无从 `co_await`。**轮询**形态则要求控件自己每帧查、样板多且易忘收口，故同样不取。回调 + 帧循环排空是本库 `NotificationCenter` 已验证的同款模式，不引入新概念。

### 剪贴板专属

3. **`Clipboard::set_offer(const ClipboardOffer &) -> Result<void>`**：注册后本进程持有剪贴板所有权，各格式的数据**在真正被读取时才经回调生成**。`formats` 为空或 `provide` 为空回调视为参数错，经既有 `general-invalid-argument` 结构化返回，不新增码。
4. **立即写与惰性声明可混用。** 既有 `set_text` / `set_payload` 等立即写通道**语义与签名完全不动**；同一份剪贴板内容上，部分格式走立即写、部分走惰性声明是**合法形态**——Win32 允许 `SetClipboardData(format, hData)` 与 `SetClipboardData(format, NULL)` 并存，macOS pasteboard 同样可混放实体数据与 promise。契约写明：惰性格式被真正请求时才调用回调，立即写的格式照旧当场落盘，两者互不覆盖。
5. **所有权丢失回调。** `Clipboard::on_ownership_lost(std::function<void()> cb) -> void`：本进程持有的所有权被其它进程夺走时调用一次，应用据此释放惰性提供所依赖的缓存与临时资源。注册新回调**替换**旧回调（不叠加，避免多注册点各自持资源；`on_change` 同款替换语义）。所有权丢失是**正常态不是故障**，故走回调而**不产出错误码**。与 `set_offer` 成对：未注册惰性要约时该回调不触发。
6. **变更监听。** `Clipboard::on_change(std::function<void()> cb) -> Result<void>`：系统剪贴板内容变化时调用（注册语义同 `on_ownership_lost`：替换不叠加）。平台无监听机制时**注册即失败**、返回新错误码 `clipboard-listen-unsupported`（**不谎报**——沿用 CHG-013 为 `available_formats()` 定下的「如实反映此刻能读到什么，不因 API 已声明就谎报可用」定调）。回调在派发线程上串行调用，实现须轻量、不得在其中触发重布局或再次读写剪贴板。
7. **程序化清空。** `Clipboard::clear() -> Result<void>`：清空系统剪贴板全部格式（清空失败走既有 `clipboard-write-failed` 口径，不新增码）。契约**显式区分**两件事——`clear()` 是「主动清空」，而空文本 / 空图像 / 空字节 / 空清单的 `set_*` 是**契约内 no-op、保留既有内容**（CHG-013 既有口径，不动）。二者语义相反，文档中并列写明以防误用。清空后 `available_formats()` 返回 `Ok(空清单)`。

### 系统拖放专属

8. **拖出会话改用事件驱动模型（本提案唯一破坏性改动，其余各条的前提）。** 现状是 `system_drag::begin(const DragOffer &)` **同步返回** `Result<DragAction>`——inert 后端立即回 `DragAction::Copy`，无后端时立即报错。真实后端接线后必然是**阻塞直到会话结束**的形态（Win32 `DoDragDrop`、Qt `QDrag::exec()` 都是嵌套模态循环）。这与本库的**单线程 UI + 帧循环**根本冲突：若 `begin()` 阻塞期间不泵帧循环，则第 10 条要加的 `on_system_drag_begin` / `on_system_drag_cancel` 与第 11 条的 Move 完成确认回调**全部无从派发**，`system_drag::cancel()` 也成了无处可调用的死接口；若泵，则引入嵌套循环的重入面。
   - **选定形态：事件驱动（GTK4 口径）**——`GtkDragSource` 不阻塞，`drag-begin` / `drag-end` / `cancel` 是主循环上的信号。**选型理由**：① 无重入，与本库「单线程 + 帧循环」的模型天然契合，不需要为嵌套泵定义重入边界；② 会话跨越多个帧 ⇒ `cancel()` 可在任意时刻调用，不必限定在回调内；③ 本库已有同款先例可循——`NotificationCenter::notify()` 同步返回 `Result<void>` 只表「投递请求是否成功」，真正的异步结果（用户点击）走 `set_on_notification_activated` 回调、由宿主每帧 `pump_events()` 排空驱动。拖出会话照此模式接线即可，不引入新概念。
   - **决定性依据：既有规格已经否掉了形态一。** `codespec/specification/06-app-platform.md` §8.9 的「拖出」条目现文明写「**不引入嵌套消息泵**」。也就是说，形态一（嵌套模态泵）不是「也可以」，而是**与既有规格直接冲突**；形态二才是与现行文档自洽的那一个。这意味着本条严格来说不是「新决策」，而是把既有承诺落到签名上——§8.9 原先把嵌套泵记为「接线期设计项」，本提案把它收敛为「不引入」，并据此定死 `begin()` 的异步签名。
   - **入口签名改为「发起即返回」**：`system_drag::begin(const DragOffer &, std::function<void(SystemDragOutcome, DragAction)> on_end) -> Result<void>`。返回值语义收窄&#x4E3A;**「会话是否发起成功」**（无后端 / 能力位为 false / 要约不合法 ⇒ 结构化 `Error`），**不再承载最终动作**；最终动作改由 `on_end` 投递。四种结局以 `SystemDragOutcome` 枚举区分：`Succeeded`（落放成功，动作有效）/ `Cancelled`（Esc 或系统取消）/ `Rejected`（目标不接受）/ `Failed`（会话中途异常终止）——**这正是当前把四种结局折叠成同一个 `DragAction::None` 的缺口所在**。
   - **`Widget::begin_system_drag()` 同步改为 `Result<void>`**（语义同为「是否发起成功」），`SystemDropPhase::Over` 的逐点反馈与既有派发规则不变。
   - **控件销毁 ⇒ 会话取消（形态二引入的生命周期契约，必须写明）**：异步会话跨越多个帧，控件完全可能在会话期间被移除。契约规定 `Widget` 析构时若本控件持有在途会话，必须调用 `system_drag::cancel()` 主动终止——这样 OS 侧不再回调 `provide`，避免要约回调访问已销毁的控件状态。回调派发前按 `HitNode` 既有的**双轨判活**处理：由 `shared_ptr` 持有的控件（`guarded` 为真）以 `weak_from_this()` 守卫、回收后跳过派发；栈 / 成员对象的控件其生命周期由持有者保证，靠上述「析构即取消」兜底。**框架不拆树时不会代调 `on_unmount`**，故此条不可省。
9. **拖拽影像。** `DragOffer` 增可选拖拽影像字段（RGBA8 位图 + 相对指针的热点偏移），由源控件在 `on_provide_drag()` 中一并给出；缺省为空表示「交给 OS 用默认影像」。该影像**只经 `begin_system_drag()` 交给 OS 合成**，本库不绘制跟随层、不新增覆盖绘制路径。不支持影像的后端静默忽略该字段、不改变会话语义。
   - **与剪贴板监听「不谎报」口径的差异，在此显式说明理由**（两条通道对同类的「机制缺失」给出不同处置，须有据可依而非各写各的）：剪贴板变更监听是**功能性契约**——注册了却收不到通知会让调用方逻辑静默失效，故必须如实报 `clipboard-listen-unsupported`；拖拽影像是**装饰性提示**——缺少它会话语义完整、只是观感降级，报错误码会逼调用方为「没有影像」写一条无意义的处理分支。**判据是「缺失后会话语义是否仍完整」**，据此不新增影像能力位（不翻 `include/aurora/window/platform.h` 的 `system_drag_in` / `system_drag_out`，两位保持接线前恒 false 的既有取值）。
10. **源侧会话生命周期回调族。** `Widget` 增 `on_system_drag_begin()`（会话已建立、进入拖动）与 `on_system_drag_cancel()`（被 Esc 或系统取消）；`on_system_drag_end` 签名改为 `(SystemDragOutcome, DragAction)`——**结局与动作一并交给控件**，语义收窄为「会话已终结」。
   - **为什么必须把结局写进签名**：只给动作时，「被拒绝」（目标不接受）与「会话失败」（中途异常）两条路径的回调序列**逐字相同**（都是 `begin` → `end(None)`），靠序列无法区分，等于没补。把 outcome 写进签名后，五种路径在控件层全部可辨——这是本次破坏性改动换来的实质收益，也是第 8 条选型能真正闭合四种结局缺口的关键。
   - **事件驱动下的派发映射唯一确定**：`Widget::begin_system_drag()` 在 `system_drag::begin()` 返回 `Ok` 后立即派发 `on_system_drag_begin()`；`begin()` 返回 `Error`（会话未建立）时直接派发 `on_system_drag_end(Failed, None)`——保留现有「失败同样要收尾」的口径（其注释明写「会话结束是控件清理拖出态的唯一时机」）。此后 `on_end` 投递时按 outcome 分派：`Cancelled` 先派发 `on_system_drag_cancel()` 再派发 `on_system_drag_end(Cancelled, None)`；`Succeeded` 派发 `on_system_drag_end(Succeeded, 动作)`；`Rejected` / `Failed` 派发 `on_system_drag_end(对应结局, None)`。
   - `system_drag::cancel()` 作为程序化取消入口（无头测试与 Esc 语义共用同一条路径），**调用时机不再受限**——事件驱动下可在任意时刻调用，有在途会话则取消，无则 no-op。
   - 逐点反馈（每帧告知当前位置与当前动作、供控件切换自身提示）按 `SystemDropPhase::Over` 已有的高频派发承载，**不新增回调**，避免与 `Over` 态双真源。回调派发前按第 8 条的双轨判活与「析构即取消」处理。
11. **Move 完成确认与回滚。** `DragOffer` 增完成确认回调：目标侧成功接收并落盘后由宿主调用，源在此回调内删除原数据；回调返回 `Error` 即代表源删除失败，宿主据此把会话终态改写为「Move 失败」并通知两侧。契约明确三条：**源不得在收到确认前删除任何数据**；**目标侧接收失败时源不得删除**；**确认回调的调用点严格早于 `on_end(Succeeded, Move)` 的投递**——事件驱动下顺序显式可断言（形态一因在嵌套泵内派发，顺序难以从外部观测，这也是选形态二的一个附带收益）。回滚能力由源自己持有（本库不代管被删数据），契约只保证「何时删」与「删失败如何上报」。
12. **修饰键与动作翻译归属。** `SystemDropEvent` 增修饰键位域（与 `MouseEvent::modifiers` 同一 `ModifierKey` 位掩码枚举、同一份真值源），由**宿主 / 后端**在构造事件时从 OS 会话写入；修饰键→`proposed` 的翻译**由宿主在派发前完成**，控件只读 `proposed` 与 `allowed`、不做翻译。这条定死之后，「谁翻译」的唯一答案是宿主，控件侧不存在第二处翻译逻辑。两项既有约定必须沿用，否则会踩坑：
   - **源侧缺省动作（本条的另一半，缺它则修饰键缺席时 `proposed` 无从确定）。** `ModifierKey::None` 在既有契约里是**两义**的——`MouseEvent` 注释明写「既可能是用户确实没按任何修饰键，也可能是本事件不由真实指针产生」，触控合成、可达性动作、诊断注入的程序化事件一律 `None`。因此**不能靠修饰键缺席推定默认动作**：`DragOffer` 增源侧缺省动作字段（对标 `QDrag::setDefaultAction`），无有效修饰键时 `proposed` 取该字段；未设置时按既有 `DragAction::Copy` 兜底。控件侧因此也获得「我不支持 Move」的表达途径——把它写进 `formats` 之外的缺省动作即可，无需另开门面。
   - **翻译前须按 `AURORA_MODIFIER_PRESSABLE_MASK` 摘除锁定态位。** 该掩码的存在就是为了「两处位集整体比较时先摘掉锁定态位，否则键盘锁定态会污染比较结果」。宿主比对 Ctrl / Shift 组合前若不先摘 `NumLock`，NumLock 开启状态下取到的位集将不等于纯 Ctrl 组合，翻译静默失效——这是 Win32 `GetKeyState` 一类返回含锁定态位的实现上的必踩陷阱。
13. **自动滚边协议。** `Widget` 增「拖入近边缘滚动意图」挂钩：宿主在 `Over` 态把落点与目标边界的距离交给命中链上的最近可滚动祖先（`ScrollViewport`，其 `ScrollGlide` 已是既有滚动动画），由后者按该动画推进；触发带宽度取 `ReorderableList::auto_scroll_threshold_` 的既有缺省（当前 48.0 dp，0 表示关闭，该值现为 `ReorderableList` 私有成员，本提案把它提出为共享缺省常量，进程内与跨进程两条拖拽路径共用一套手感）。**不新增滚动实现**，只补「拖入时谁驱动滚动」的契约。
14. **读取失败的反馈口径。** 契约写明：`Drop` 态读取失败时，宿主把会话终态置为失败并派发终态回调，控件须给出**非光标**的可见反馈（与 §5.2 已有的「放置反馈不得只靠光标形态表达」同款要求）；读取失败**不重试自动兜底**，重试决策归控件（错误码 `retryable` 已给出依据）。
15. **无障碍从文档层升到契约层。** `codespec/specification/05-event-navigation.md` §5.2 已有一句文档层承诺（拖放不是唯一路径、放置反馈不得只靠光标）。本提案把它升为可验收契约：可接收拖放的控件须同时提供非拖拽入口声明（`Widget` 增一个返回替代路径描述的查询，缺省为空表示「本控件只有拖拽一条路」，工具与无障碍桥据此告警；该查询**与既有 `AccessibilityNode` 角色动作体系分工**，只补「替代路径」这一项，不重复表达控件语义），缺失在门禁侧可被检出而非仅靠人工评审。


### 错误码与测试

16. **错误码扩充（只增不改，共六枚）。** 重生成 `include/aurora/core/error_codes.gen.h` 与 `codespec/ERROR_CATALOG.md`：
    - `clipboard-provider-failed`：惰性提供的回调返回 `Error`，或回调为空而格式被真正请求（category = platform、severity = error、retryable = **false**——与既有 `clipboard-write-failed` 同口径：同一笔数据是否重试由应用决定，库不代做重试）；

    - `system-drag-read-failed`：载荷读取失败（源会话失效、字节不可得；category = platform、severity = error、retryable = **true**——同一格式重试一次可能成功，与「机制缺失」的稳态性质不同）；

    - **破坏性改动清单（因第 8 条改走事件驱动而引入，落地时须逐条记入 `CHANGELOG.md` 的 Breaking 条目并给迁移路径）**：

      | 破坏点 | 改前 | 改后 | 迁移路径 |
      |:---|:---|:---|:---|
      | `system_drag::begin` 返回类型 | `Result<DragAction>` | `Result<void>` | 取最终动作改为在 `on_end` 回调里取 |
      | `system_drag::begin` 形参 | `(const DragOffer &)` | `(const DragOffer &, on_end)` | 补传终结回调；不关心结果可传空回调（会话照常，只是收不到终态） |
      | `Widget::begin_system_drag` 返回类型 | `Result<DragAction>` | `Result<void>` | 同上；原本靠返回值判断落放结果的调用方，改在 `on_system_drag_end` 里判断 |

### 剪贴板平台接线（追加批次）

19. **立骨期边界到此收口。** 前 18 条交付的是**契约**：`set_offer` / `on_ownership_lost` / `on_change` / `clear` 与六枚错误码的定义齐全，但七枚富格式读写在测试后端分支之外**一律返回格式不支持**——那是立骨时写死的边界，不是缺陷。本批次把这七枚接到真实平台，剪贴板富格式才从「API 已声明」变成「平台真的通」。接线**不改任何签名与语义**（第 18 条的排除项继续成立），只补平台实现；第 3 条「立即写与惰性声明可混用」、第 5 条「所有权丢失是正常态不是故障」、第 6 条「无机制即如实报错」三条定调在接线后逐条继续成立。
20. **Win32 实现。** 文件清单走 `CF_HDROP`；`uri-list` / HTML / 自定义 MIME 经 `RegisterClipboardFormat` 注册后按格式名读写，HTML 按 `CF_HTML` 的既有组帧规则封装；惰性提供落 `SetClipboardData(format, NULL)` + `WM_RENDERFORMAT`（与第 3 条混用契约的 Win32 依据同款）；变更监听落 `AddClipboardFormatListener` / `WM_CLIPBOARDUPDATE`；所有权丢失落 `WM_DESTROYCLIPBOARD`。全部经 `Win32Host` 现有消息泵承接，不新增窗口类、不引入嵌套泵。
21. **macOS 实现。** `NSPasteboard` 承担实体数据与 promise 两种写入（对应第 3 条的混用契约），文件的延迟兑现走 `NSFilePromiseProvider`；变更监听走 `changeCount` 轮询——AppKit 不给变更通知，`NSPasteboard` 的变更只经计数暴露，轮询点复用既有「帧内排空、不在消息泵内回调」纪律，不新开线程；所有权丢失由 pasteboard 的所有权变更语义给出。**与菜单栏、最近文档同源的处境**：真机验收依赖 macOS 后端窗口壳实写，故机制层先行、真机段留白，不在没有真机的地方写推断当事实。
22. **X11 / Wayland 实现。** 两后端共用 Selection 语义：所有权经 `TARGETS` 协商、格式按 MIME 名匹配、惰性提供由 selection owner 在收到请求时经 `provide` 回调产出字节；Wayland 侧另经 `wl_data_device` 的 selection 事件承载所有权变更与变更监听。两后端**不引入任何新第三方依赖**（沿用各自既有的 X 与 wayland-client 面）。

    **Linux 接线注记（2026-10-28 落地）**：文本 / 图像 / `clear()` 继续走既有 `xsel` / `xclip` 路径；富格式与惰性提供走 `src/aurora/window/detail/x11_clipboard.{h,cpp}` 与 `wayland_clipboard.{h,cpp}`，与 `xsel` 落到同一 CLIPBOARD 选择、后写者接管。变更监听：X11 需 XFIXES 扩展（构建期要求找到 `libXfixes` 并显式链接，运行期缺扩展时 `on_change` 如实报 `clipboard-listen-unsupported`），Wayland 由 selection 事件恒支持。**依赖口径修正**：第 22 条「不引入任何新第三方依赖」按「不引入新生态」读——XFIXES 属 X11 系但为独立库，`FindX11` 的 `X11_LIBRARIES` 不含它，`cmake/AuroraBackends.cmake` 已改为配置期硬要求；Wayland 侧确无新增依赖。Wayland 的 `wl_data_device` 每 seat 唯一：剪贴板桥复用拖放桥创建的那一枚，selection offer 归剪贴板桥销毁。协议顺序实测为 `data_offer` → 逐个 `offer`（MIME 名）→ `selection`，转发器因此在 selection 时交 offer 连同已收集的名称；对不合规合成器先发 selection、后补名称的情形，转发器按增量补发名称而非静默丢弃。**两处协议约束**：Wayland `set_selection` 必须携带真实输入事件 serial，libwayland 公开 API 不提供当前 serial，故表面在指针按键 / 键盘按键路径记账 `last_input_serial`、桥经 hooks 取用，无 serial 时如实报 `clipboard-write-failed` 且不声明所有权（不伪造 serial）；XFIXES 的 selection 通知在 `XEvent` 联合里没有成员，桥按结构体前导布局 `memcpy` 解出。macOS 腿仍留白，归另一批次。
23. **如实申报的边界随接线收窄。** 接线完成后，`clipboard-format-unsupported` 只在「该平台确实没有对应格式」时成立；「本平台有但本库没实现」与「本平台没有」是两件事，混在一起就是谎报——这正是第 6 条为变更监听定下的定调，接线后同样适用于格式。接线前那句「机制落地前不入列」的立骨期声明随之作废并在规格侧改写。
24. **不落本批**：拖入侧图像的 `CF_DIBV5` → PNG 转码（属系统拖放域，与系统拖放桥的边界重合，避免两处各实现一份）、HTML 内容的清洗与重写（应用侧责任，库只保证字节往返）、Windows 自定义 JumpList 的最近文档类别（属最近文档域）。

## 验收判据

1. **惰性按需兑现（剪贴板）**：经 memory 后端注册含三种格式的要约，**断言注册后回调一次都未被调用**；随后逐个格式读取，断言每个格式各自触发一次回调、且只带该格式的 `mime` 入参。**变异自证**：把 `set_offer` 改为注册时立即兑现全部格式，注册后零调用这一条必须转红——绿不算证据。另断言参数错口径：`formats` 为空或 `provide` 为空回调时 `set_offer` 返回 `general-invalid-argument` 而非静默成功。
2. **立即写与惰性混用**：同一份内容上一格式走 `set_payload` 立即写、另一格式走要约惰性声明，断言两者都能被读到且结果各自正确、互不覆盖；立即写的格式不触发惰性回调。
3. **所有权丢失**：memory 后端模拟所有权被夺，断言回调被调用且**只被调用一次**；未注册惰性要约时该回调不触发；重复注册新回调后旧的不再被调用（替换语义）。
4. **变更监听**：memory 后端模拟内容变化，断言回调触发；平台无监听机制时 `on_change` 返回 `clipboard-listen-unsupported` 而非静默成功。**变异自证**：把「无机制」分支改为返回 `Ok`，该用例必须转红（证明「不谎报」是可观测判据而非文档承诺）。
5. **提供与读取失败口径**：剪贴板回调返回 `Error` 时读取侧拿到 `clipboard-provider-failed` 而非既有三枚之一；拖放侧读取失败拿到 `system-drag-read-failed`、解码失败拿到 `system-drag-decode-failed`，均非既有两枚 slug；拖放侧控件收到非光标的可见反馈（以反馈状态位断言）。
6. **清空与 no-op 相反**：`clear()` 后 `available_formats()` 为 `Ok(空清单)`；而空串 / 空清单 / 空字节的 `set_*` 后**既有内容原样保留**（既有 no-op 口径不退化，逐格式断言内容不变）。
7. **两条通道要约同构**：`ClipboardOffer` 与 `DragOffer` 字段形态一致（格式清单 + 同签名的 `provide`），MIME 取值同出自 `include/aurora/app/mime_types.h`——用例以「同一个 `provide` 回调同时交给两条通道且结果一致」锁定这一对称关系，这是「同一套词汇不在两条路径上各长一次」的锚点。
8. **读取不卡帧（两条通道里最致命项的判据）**：`Drop` 态经非阻塞入口读取一大载荷（用例内构造 ≥ 8 MiB 的自定义 MIME 载荷），断言读取期间帧循环推进次数 ≥ 1 且单次同步调用不产生跨越一整帧的停顿；同步入口对同一载荷仍返回全等字节（两条通道结果一致）。**判据须经 `SystemDropEvent` 的便利读取走一遍再经 `DragPayload` 直连走一遍**——只测后者会漏掉「事件层没同步扩出非阻塞通道」这个缺口。**变异自证**：把非阻塞入口改回同步实现（读取期间不退回帧循环），该用例必须转红。
   - **并发读取不互相取消**：同一 `shared_ptr<const DragPayload>` 复制出两个持有者，各自发起一次非阻塞读取，断言两次回调各自被调用且**只被调用一次**、结果各自全等（验证边界五的「各自独立登记、各自兑现」语义，防共享在途项导致一方被另一方取消）。
   - **回调在帧内排空、不在消息泵内回调**：断言回调执行时帧循环处于排空阶段（以「排空阶段标记」断言），而非平台事件派发栈内——这条钉住的是与第 8 条同源的防重入口径。**变异自证**：把兑现改到平台消息泵内同步回调，该用例必须转红。
   - **兜底兑现与只调一次**：发起读取后不排空帧循环、直接结束会话，断言在途读取**被就地兑现**（回调被调用一次且只一次、给出空口径或失败），不得悬挂。断言回调执行后在途项被摘除（同一会话内二次收口不再触发回调）。
   - **宿主不排空 ⇒ 回调不到（不谎报）**：发起读取后不调用排空入口，断言回调**未被调用**且读取不谎报成功——与 `NotificationCenter` 的同名口径一致。**变异自证**：把「未排空」分支改为立即以 `Ok` 兑现，该用例必须转红。
   - **墙钟超时**：源侧始终不给数据时，断言超过约定时长后回调以 `system-drag-read-failed` 兑现（非静默悬挂、也非谎报成功），且不新增专用错误码。
9. **拖放空口径与失败口径不退化**：读不存在格式 = `Ok` 空值；非 `Drop` 态访问载荷 = 空口径且不崩溃；会话结束后在途读取按兑现规则收口（断言无悬挂句柄，以读取回调被调用且只被调用一次为准）。
10. **拖拽影像**：`DragOffer` 带影像与热点偏移发起会话，inert 后端记录到影像字节与偏移且逐字段相等；不带影像时后端记录到「缺省」且会话语义不变。
11. **会话回调序列（五种路径的完整序列与 outcome 组合，缺一即判据不全）**：

    | 路径 | `begin()` 返回 | 回调序列 |
    |:---|:---|:---|
    | 成功落放 | `Ok` | `begin` → `end(Succeeded, 协商出的动作)` |
    | 被取消（Esc / 系统取消） | `Ok` | `begin` → `cancel` → `end(Cancelled, None)` |
    | 被拒绝（目标不接受） | `Ok` | `begin` → `end(Rejected, None)` |
    | 会话中途异常终止 | `Ok` | `begin` → `end(Failed, None)` |
    | 发起失败（无后端 / 能力位 false / 要约不合法） | `Error` | `end(Failed, None)`（**无 `begin`**） |

    断言要点：① `on_system_drag_cancel` **只**出现在被取消路径，且严格早于 `on_system_drag_end`；② 「被拒绝」与「会话中途异常」的**回调序列逐字相同**，靠 `SystemDragOutcome` 区分——**正因如此 outcome 必须进签名**（见第 10 条）；③ 「发起失败」与「会话中途异常」的区别**恰在有无 `begin`**；④ 五种路径的「序列 + outcome」组合两两不等。**变异自证**：把 outcome 从签名里去掉、退回只传动作，「被拒绝」与「会话中途异常」两条路径立刻不可分辨——该用例必须转红。
    - **`end` 的无条件性不得退化**：发起失败路径**仍须派发 `end(Failed, None)`**（沿用现有「会话结束是控件清理拖出态的唯一时机，失败同样要收尾」的口径）——断言这一条，防止后续重构把失败路径的收尾回调一并删掉。
12. **拖出会话执行模型（事件驱动的落地判据）**：
    - **`begin()` 不阻塞**：断言 `system_drag::begin()` 在 inert 后端下**立即返回**、不等待会话结束；返回值语义为「是否发起成功」（`Ok` 不等于落放成功）。**变异自证**：把 `begin()` 改回阻塞到会话结束、同步返回动作，该用例必须转红——这条钉住的是整个模型形态，是第 8 条的开关。
    - **回调在帧循环上派发**：从发起会话到 `on_end` 投递之间，断言帧循环推进次数 ≥ 1（证明终结事件是经帧循环排空驱动的，而非 `begin()` 返回后同步补发）。
    - **`cancel()` 时机不受限**：在会话外（无在途会话）调用 `system_drag::cancel()`，断言为 no-op 且不影响后续会话；在会话进行中于帧循环上调用，断言会话终态为 `Cancelled`。
    - **控件销毁 ⇒ 会话取消（第 8 条生命周期契约）**：发起会话后销毁发起控件，断言会话被取消、且此后 `provide` 回调**不再被调用**（以 inert 后端记录断言）；控件由 `shared_ptr` 持有时，断言终结回调被跳过而非解引用已回收对象。
    - **无重入**：在 `on_system_drag_begin` 内执行一次会改动控件树的写操作，断言不触发嵌套派发、树状态与操作意图一致（形态二相对形态一的收益点，钉住「无嵌套泵」这一性质）。
13. **Move 语义**：目标接收成功后源删除回调被调用一次，且**调用发生在 `on_end(Succeeded, Move)` 投递之前**（以回调调用序号断言）；删除回调返回 `Error` 时会话终态改写为 Move 失败并上报 `system-drag-move-rollback`，且目标侧数据保持不动。**变异自证**：把确认回调的调用点后移到 `on_end` 投递之后，序号断言必须转红——这条钉住「源不得在收到确认前删除数据」，也顺带证明事件驱动下调用顺序是**从外部可观测**的（形态一在嵌套泵内派发，顺序无从断言，这是选形态二的附带收益）。
14. **修饰键翻译（含修饰键缺席与锁定态污染两路，只测「有修饰键」等于只测了半边）**：
    - **有修饰键**：构造带 Ctrl 的 `Over` 事件，断言宿主写入的 `proposed` 为 `Copy`、带 Shift 为 `Move`；断言控件侧不存在第二处翻译（以「不重写 `proposed`」的单点写入为准）。
    - **修饰键缺席（另一半）**：构造 `modifiers == ModifierKey::None` 的事件，断言 `proposed` 取 `DragOffer` 的源侧缺省动作字段；该字段未设置时按 `DragAction::Copy` 兜底。**变异自证**：把缺省动作字段的读取改回「由 `modifiers` 缺席推定 `None`」，该用例必须转红——这条钉住的是「`None` 两义 ⇒ 不可推定」这个契约事实：`None` 既可能是用户没按、也可能是程序化事件，靠它推默认动作会把合成事件误判成「用户明确不要动作」。
    - **锁定态污染（实现陷阱）**：构造 `Ctrl | NumLock` 的事件，断言翻译仍得到 `Copy`（验证宿主按 `AURORA_MODIFIER_PRESSABLE_MASK` 摘除锁定态位后再比对）。**变异自证**：去掉掩码摘除步骤，该用例必须转红——不钉这条，NumLock 常开的实现上（Win32 `GetKeyState` 一类返回含锁定态位）会静默失效且本地难复现。
15. **自动滚边**：在 `ScrollViewport` 内构造落在近边缘触发带内的 `Over` 事件，断言滚动量按帧推进且方向与边缘一致；落点在带外时不推进。触发带宽度与 `ReorderableList` 的同名缺省值相等（当前 48.0 dp，两条拖拽路径手感一致的锚点）。
16. **无障碍契约**：替代路径查询缺省为空；覆写返回非空后工具侧可检出；未覆写的控件在无障碍桥中被标记为「仅拖拽可达」（以桥侧记录断言）。
17. **门禁与全量测试**：`--target aurora_api_json` 重建后 `check_api_schema_sync` 零漂移；`check_api_budget` 增量评估通过；`check_naming_conventions` / `check_doc_comments` / `check_platform_macros` / `check_no_cjk_literals` / `check_no_hardcoded_paths` / `check_core_layer_boundary` / `check_codespec_xref` / `check_code_doc_sync` / `check_change_proposals` 全绿；`lint`（仅改动相关 TU，先 `--print-tus` 确认集合）与 `format-check` 绿；全量 `ctest -j16` 绿。
18. **平台富格式往返（真实后端）**：Win32 上 `set_files` / `get_files` 往返逐条一致（顺序与分隔符口径按 `uri-list` 既有编解码）；`set_html` / `get_html` 往返按 `CF_HTML` 组帧规则保真；自定义 MIME 写入后 `available_formats()` 如实包含该格式。**变异自证**：把注册格式名写错一位，往返与格式清单两条必须同时转红——只红一条说明其中一条是空断言。
19. **惰性提供在真实平台按需兑现**：Win32 上注册惰性要约后，断言 `WM_RENDERFORMAT` 到来前 `provide` 一次都未被调用；触发读取后被调用一次且只带被请求的格式。所有权被其它进程夺走时 `on_ownership_lost` 触发一次。**变异自证**：把惰性改成注册即兑现，「到来前零调用」必须转红。macOS 与 X11 / Wayland 两腿按各自机制层可证的部分登记，真机段（macOS）留白。
