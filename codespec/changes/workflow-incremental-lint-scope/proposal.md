# CHG-008 lint 门禁按改动选集：分支跑受影响 TU，全量留给主线与定时兜底

| 项目 | 内容 |
|:---|:---|
| 变更编号 | CHG-008 |
| 提出日期 | 2026-10-09 |
| 当前状态 | 已归档 |
| 关联需求 | 无 |
| 影响面 | CI 静态检查门禁（`lint` / `lint-wasm` 作业）、`tools/check/` 脚本；不改库代码与公共 API |

## 动机

静态检查门禁的墙钟 = TU 数 × 单 TU 分析成本 ÷ 并行度。分片（pass × shard = 8 个作业）把
整门墙钟从 86 分钟压到 ~25 分钟，但**每个 PR 仍要为它没碰过的代码付一次全量代价**：改一个
头文件与改五百个文件，CI 跑的是同一批 498~556 个 TU。runner 只有 4 vCPU，这个代价直接换算成
每个 PR 的等待时间，于是「门禁很慢」变成了「少跑一点」的压力来源——而少跑又只能靠放宽判据，
那正是门禁最不该走的方向。

本次要买的是另一半：**改什么就只重跑读到它的那些 TU**。判据不变（仍然是 0 finding 才过），
变的只是「这一轮把判据施加在哪些 TU 上」。可行性来自一条事实——clang-tidy 的诊断只可能来自
TU 自身与它读到的头文件，没被挑中的 TU 本轮不可能因为本次改动而产生新告警。

## 变更内容

**选集（方案 B）**：新增 `tools/check/select_lint_tus.py`。输入改动清单，输出
`selection.json` / `deps.json` / `tus_<i>.txt`。判定依据是**编译库自身的 include 闭包**
（对每条编译命令跑一次 `-MM`），不是构建图：

- `ninja -t deps` 只认**已经构建过**的目标，而 demos 是 `EXCLUDE_FROM_ALL`——它们不在构建图
  里，却实实在在在编译库里、也实实在在会因为改一个公共头而产生新告警。本机实测：
  `include/aurora/event/keycode.h` 的一条 `readability-string-compare` 正是从
  `examples/app/google_play/demo_google_play.cpp` 这个 TU 报出来的，按构建图选集会正好漏掉它。

三条「宁可多选、不可漏选」的兜底：取依赖失败的 TU 一律入选；改动里出现**已不存在**的文件
（删头，删后闭包算不出来）退化为全量；改动命中「全局配置」（`.clang-tidy`、CMake 模块、
本脚本与 runner 自身）退化为全量——这类文件改的是**分析口径本身**，选任何子集都是错的。

反向守卫是本脚本唯一会退出码 2 的情形：**改动里存在本编译库认得的 C/C++ 文件，却一个 TU
都没选中**。逻辑上不可能（认得 = 是 TU 或被某个 TU 包含），一旦发生说明选集链路坏了，必须红。

**结果缓存（方案 C）**：`run_clang_tidy.py` 新增 `--cache-dir` + `--deps` + `--tu-list`。
指纹 = clang-tidy 版本 + 编译器版本 + `.clang-tidy` 内容 + 该 TU 的编译 argv + TU 自身内容
+ 其依赖逐文件内容；命中即复放上一次的原始输出（不是「记为通过」）。两条硬边界：编译失败
或超时的 TU **绝不入缓存**（把「0 告警」写进缓存等于把覆盖面塌方固化成永久绿灯）；依赖清单
里没有的 TU 不缓存（指纹会退化成只看自身内容，那是本缓存唯一能造出的假绿）。

**CI 编排**：`lint` 与 `lint-wasm` 新增「Decide lint scope」步骤——master 推送、每周定时与
手动触发跑全量，PR 与功能分支推送走增量；取不到基线提交（浅克隆 / 首次推送）一律**退化为
全量**并留 warning，绝不退化成空集。增量路径下子集按 `--min-tu-per-shard` 少分片，多出来的
片显式写 `idle` JSON 后退出 0（「没活儿」与「跑过且干净」在日志里长得一样，必须留痕）。

公共面变化：无。本提案只动 CI 编排与 `tools/check/` 脚本，库代码与公共 API 一字未改。

## 验收判据

1. **选集不漏**：对「改动 `include/aurora/event/keycode.h`」这一输入，选出的 TU 集合必须包含
   所有读到该头的 TU——含 `examples/app/google_play/demo_google_play.cpp`（构建图法会漏掉它）。
   本机实测：该批改动（10 个 C/C++ 文件）选中 184/556 个 TU，且 10 个改动文件全部落在
   `applicable_cpp` 里、无 unmatched。
2. **缓存不改变结果**：同一份 TU 清单连跑两轮，第二轮 `cache: N hit / 0 miss`，两轮
   `findings` 逐条相等（本机实测 10 TU：92s → 0.38s，findings 全等）。
3. **指纹随依赖变**：改动某个 TU 的依赖文件内容后，该 TU 的指纹必须变化；依赖清单里没有的
   TU 的 `key_for()` 必须返回 None（不可缓存）。
4. **空集必红**：改动里含本编译库认得的 C/C++ 文件却选中 0 个 TU 时，脚本以退出码 2 失败。
5. **全量出口仍在**：`master` 推送、每周定时与手动触发三种事件下，两个 lint 作业仍走
   `cmake --build --target lint` 的全量路径。
