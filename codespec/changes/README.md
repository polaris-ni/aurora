# 变更提案契约

> 本文件是 `codespec/changes/` 的唯一权威说明，格式由 `check_change_proposals.py` 守护
> （已接入 `ctest --preset ninja-test`）。改契约必须同时改文档与脚本。

---

## 1 为什么要有落盘的提案

Aurora 的既有闭环解决的是「文档与代码不漂移」：`check_codespec_xref` 与
`check_code_doc_sync` 双向校验文档与代码实体，需求 ID 体系给出稳定标识。缺的一环是
**动手之前的共识**——决策此前只存在于对话里，不进仓库、不可评审、不可回溯。

本目录补的就是这一环：任何触及公共 API、分层边界、后端矩阵或性能门槛的改动，先落一份
提案，达成共识后再落码。它是**评审载体**，不是任务清单，因此不写任务编号、不写阶段号。

与 OpenSpec 之类外部工具的关系：本目录只吸收「变更提案」这一个点，用仓库自有的需求 ID
与章节号体系表达，不引入额外工具链，也不复制 `codespec/` 已有的规范正文——
`codespec/specification/` 仍是规范权威，`changes/` 只记录「这次要改什么、改完回写到哪」。

---

## 2 目录与文件

```
codespec/changes/<语义短名>/proposal.md
```

- `<语义短名>` 为 kebab-case（小写字母与数字，用单个连字符连接），例如
  `hit-test-extra-box`。它是提案被引用时的稳定把手，会出现在路径、提交信息与文档引用里。
- 每个提案目录**必须**含 `proposal.md`。设计细节与实施清单可另附 `design.md` / `tasks.md`，
  门禁不校验二者。
- 提案不搬进 `archive/` 子目录：状态靠元信息字段表达，路径永不变动，既有引用不会失效。

## 3 proposal.md 结构

### 3.1 标题与元信息表

首行一级标题为 `# CHG-<NNN> <标题>`，`<NNN>` 为三位数字。编号全局唯一，且按目录名字典序
升序分配（缺口只可能来自被放弃的提案，不重排）。

紧随其后是二列元信息表，**五个字段、固定顺序、均不可为空**：

| 项目 | 内容 |
|:---|:---|
| 变更编号 | CHG-001 |
| 提出日期 | 2026-10-05 |
| 当前状态 | 已提议 |
| 关联需求 | 无 |
| 影响面 | 命中测试链路与覆盖绘制控件 |

字段取值域：

| 字段 | 取值域 |
|:---|:---|
| 变更编号 | 必须等于标题中的 `CHG-<NNN>` |
| 提出日期 | `YYYY-MM-DD` |
| 当前状态 | 已提议 / 实施中 / 已归档 / 已放弃 |
| 关联需求 | `无`，或 `SPECIFICATIONS.md` 特性表中真实存在的需求 ID |
| 影响面 | 自由文本，说明受影响的模块或后端 |

### 3.2 正文四节

以下四节**必须齐全、顺序固定、均不可为空**：

| 节 | 写什么 |
|:---|:---|
| 动机 | 为什么改，现状哪里不成立 |
| 变更内容 | 改什么，含公共面变化与破坏性说明 |
| 验收判据 | 可判定的判据，至少一条；禁止占位符 |
| 回写落点 | 至少一条 `codespec/...` 相对路径，且文件真实存在 |

`回写落点` 是硬要求而非建议：改完不回写文档会直接触发
`check_code_doc_sync` 与 `check_codespec_xref` 红灯，提案阶段就必须说清落到哪一份文档。

## 4 状态流转

```
已提议 -> 实施中 -> 已归档
   |         |
   +---------+-> 已放弃
```

- **已提议**：草稿，等待评审。
- **实施中**：共识达成，正在落码。
- **已归档**：改动已合入，且回写落点已按 §3.2 更新完毕。
- **已放弃**：不做了。编号保留、不复用、不重排，以便历史引用继续可达。

---

## 5 门禁

```
python3 tools/check/check_change_proposals.py --root .
ctest --preset ninja-test -R check_change_proposals
```

覆盖：目录命名、提案文件存在性、标题形态、编号唯一与升序、元信息五字段与取值域、
关联需求是否真在特性表、四节齐全与顺序、验收判据非空、回写落点路径真实存在。

无提案时门禁直接通过——它只约束「写了的」，不强制「必须写」。
