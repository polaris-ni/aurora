## 1 适用范围与约定

### 1.1 被测模块

`image/` —— Aurora 的**图片编解码层**，在实测依赖分层中位于 L1（其公共头只依赖 `core`）。

公共头只有 1 个：`include/aurora/image/image_codec.h`，提供：格式枚举与嗅探（`ImageFormat` / `detect_format` / `format_from_path`）、解码选项（`DecodeOptions`）、编解码器抽象与注册表（`ImageCodec` / `ImageCodecRegistry`）、动图容器（`AnimatedImage`）、异步解码（`decode_async`）与一组便捷自由函数。

> `include/aurora/core/image.h` 是**图像数据结构**（`Image`：width / height / RGBA8 像素），归 core 模块，不在本模块范围内；但其 `Image::load` 委托本模块的 `ImageCodecRegistry` 统一调度，因此本模块的可观测行为会经 `ImageView` 落到窗口上。

**实测启用的编解码后端**（取自 `ImageCodecRegistry` 构造与本次构建的 `build/CMakeCache.txt`）：

| 编解码器（注册名） | 格式 | 解码 | 编码 | 接入条件 |
|:---|:---|:---:|:---:|:---|
| `bmp` | BMP（仅未压缩 24 位） | 是 | 否 | 始终注册（内置） |
| `svg` | SVG（内置子集光栅化） | 是 | 否 | 始终注册（内置） |
| `stb` | PNG / JPEG / GIF / TGA / HDR（按魔数嗅探） | 是 | 否 | 始终注册（内置，零三方依赖） |
| `png-write` | PNG | 否 | 是 | 始终注册（内置最小化编码器） |
| `jpeg-turbo` | JPEG | 是 | 是 | `AURORA_ENABLE_IMAGE_JPEG=ON`（实测 **OFF**） |
| `webp` | WebP | 是 | 是 | `AURORA_ENABLE_IMAGE_WEBP=ON`（实测 **OFF**） |
| `png-wuffs` | PNG | 是 | 否 | `AURORA_ENABLE_IMAGE_PNG=ON`（实测 **OFF**） |
| `gif-wuffs` | GIF（含动图帧序列） | 是 | 否 | `AURORA_ENABLE_IMAGE_PNG=ON`（实测 **OFF**） |

由此得到的**默认构建能力口径**，是本文档各用例预期的前提：

- PNG、JPEG、GIF 均可解码（走 `stb`）；GIF 只解出单帧（无动图解码器注册）。
- PNG 可编码（走 `png-write`）。
- **WebP 在默认构建下没有任何解码器** —— 这是 §2.4 中「不支持格式」用例的输入来源。
- BMP 只有「未压缩 24 位」一种形态受支持，其余位深/压缩变体由 `bmp` 解码器明确拒绝。

### 1.2 执行载体

复用既有窗口 demo `examples/demos/demo_image_view.cpp`（构建目标 `demo_image_view`），**不新增载体**。

该 demo 经 `examples/demos/demo_common.h` 的 `run_demo` 创建窗口（标题 `ImageView · Aurora Demo`，尺寸 520×420），主体是一个 `ImageView`；解码失败时整块换成占位文本节点，不打印错误详情。

载体有一个关键行为，决定了本文档切换被测格式的方式：它固定读取**工作目录下的 `test.bmp`**，但 `ImageCodecRegistry::decode_file` 先读入字节再按**内容魔数嗅探**派发解码器，与扩展名无关（扩展名只在 `save()` 路径上用于兜底）。因此：

- 切换被测格式 = 把该格式的文件复制成工作目录下的 `test.bmp`，无需改扩展名、无需改代码。
- 反之，**文件名不能作为「被测格式」的证据**，判定一律以文件内容为准。

### 1.4 用例编号规则

格式 `TC-<模块段>-<三位序号>`，自 001 起连续编号。
模块段为**模块目录名的大写形式**（`core` → `CORE`、`i18n` → `I18N`；取 `include/aurora/` 下的模块目录名，本目录文件名前缀 `NN-` 是文档序号、不计入模块段，如 `01-core.md` → `CORE`），**不得自创缩写**——目录名含数字时数字原样保留，故正则为 `^TC-[A-Z0-9]+-\d{3}$`。
本模块目录名 `image`，即 `TC-IMAGE-001` 起。序号在本模块内唯一且**不复用**；用例被删除后其编号作废，新用例取下一个可用序号。
用例在文档中**按编号升序声明**——该顺序即默认执行顺序，也是依赖列表排序的依据（见 §1.5）。

### 1.5 用例字段清单与格式规范

每条用例由**六个固定字段**组成，排布于同一张 Markdown 表格内。**字段顺序固定、字段名一字不差、每字段独占一行、单元格内不换行**（需要多条内容时用 `<br>` 分隔）：

| 序号 | 字段 | 格式 | 正则约束 | 说明 |
|:--:|:---|:---|:---|:---|
| 1 | 用例编号 | 单行 | `^TC-[A-Z0-9]+-\d{3}$` | 模块内唯一且不复用 |
| 2 | 测试目的 | 单行 | 自由文本 | 一句话，指向**单一**验证目标 |
| 3 | 前置条件 | 单行 | 自由文本 | 只描述**环境状态**；「必须先执行某用例」属依赖用例字段，不在此重复 |
| 4 | 依赖用例 | 单行 | `^无$` 或 `^TC-[A-Z0-9]+-\d{3}(, TC-[A-Z0-9]+-\d{3})*$` | 见下方规范 |
| 5 | 操作步骤 | 条目列表 | 每条目以 `^\d+\. ` 开头，条目间以 `<br>` 分隔 | 自 1 起连续编号 |
| 6 | 预期结果 | 条目列表 | 同操作步骤；编号是步骤号的**子集** | 见 §1.6 |

**依赖用例字段规范（四条硬性要求）：**

1. 无依赖时**必须**写 `无`，不得留空、不得写 `-`、`N/A`、`none` 等变体。
2. 有依赖时写**用例编号全称**（含模块段），不写省略形式；跨模块依赖同样写全称。
3. 多项依赖以**半角逗号加一个空格**（`, `）分隔；逗号前后不得出现空格以外的字符。
4. 多项依赖的**排列顺序即依赖先后**——先决者在前。因用例按编号升序声明，等价于按被依赖用例的**编号升序**排列。

**模块级约定**：本模块载体的构建步骤统一置于 `TC-IMAGE-001` 的步骤 1；其余用例不在步骤中重复构建，而是通过依赖用例字段间接依赖其产出的已构建载体。

**为什么必须统一格式**：本文件由 `tools/check/check_manual_test_format.py` 解析守护（CTest 用例 `check_manual_test_format`，校验字段名与顺序、取值域、依赖拓扑、步骤-预期同号映射与执行记录表格式）。上述约定使每个字段可用**单条正则**校验，无需自然语言推断。

### 1.6 操作步骤与预期结果编号规则

**预期结果与操作步骤同号一一对应**：`预期结果 N` 即「步骤 N 的对应结果」。

1. 预期结果的序号**等于**其对应步骤的序号，两者严格相等——不得因省略而重排、压缩或重新连续编号。
2. 纯执行步骤**不产生预期结果**，其序号在预期结果列表中直接跳过。
3. 故预期结果的序号**不要求连续**，条数也无需等于步骤数。
4. 步骤列表中，纯执行步骤在文本末尾标注「（纯执行，无预期结果）」，供与预期结果列表逐号对照。

示例：某用例有步骤 1、2、3、4，其中步骤 3 为纯执行步骤，则该用例的预期结果共 3 条，编号为 1、2、4。

**该规则解决的问题**：执行者按步骤顺序推进时，编号本身即是映射关系，无需自行推断「这条预期结果对应哪一步」；执行记录可借步骤号精确落到失败点。

### 1.7 判定与记录

| 结果 | 含义 |
|:---|:---|
| PASS | 全部非空预期结果均满足 |
| FAIL | 任一非空预期结果不满足；须在记录表登记该预期结果对应的**步骤号**、实际现象与缺陷编号 |
| BLOCKED | 前置条件无法满足（如载体构建失败），未开始执行 |
| SKIP | 主动判定不适用于本环境（如构建开关与用例前提不符） |

输出中含**时间戳、线程 id** 的字段属可变部分，判定时只核对格式与是否出现，不比对具体值。

**执行记录表格式**（列顺序固定）：

| 列 | 格式 | 允许值 / 正则 |
|:---|:---|:---|
| 用例编号 | 单行 | 与 §2 用例编号一致 |
| 执行日期 | 单行 | `^\d{4}-\d{2}-\d{2}$` |
| 执行人 | 单行 | 自由文本 |
| 结果 | 单行 | `PASS` / `FAIL` / `BLOCKED` / `SKIP` |
| 失败步骤号 | 单行 | 留空（未失败或未执行），或 `^\d+(, \d+)*$`（多个以半角逗号加一个空格分隔） |
| 实际现象 | 单行 | 自由文本 |
| 缺陷编号 | 单行 | 留空或缺陷单号 |
| 备注 | 单行 | 自由文本 |

未执行的取值一律**留空单元格**，不写 `-`、`TBD`、`N/A` 等占位符。

### 1.8 覆盖取舍

本模块按「人工判定是否优于程序判定」取舍。

**纳入人工测试的子域**（人工能判得比程序准）：

| 子域 | 人工判定优于程序判定的原因 |
|:---|:---|
| 解码后图像的视觉正确性 | 是否偏色、通道是否互换、上下是否颠倒，是「看图」判断；断言只能比对已知像素，对未知素材无能为力 |
| 透明通道与半透明合成 | 透明区是否透出底色、半透明是否呈中间调、边缘有无黑边/光晕，属观感判断 |
| 缩放后的清晰度 | 是否糊、有无阶梯锯齿或摩尔纹，**没有可断言的标量指标**，只能人眼判 |
| SVG 不同声明尺寸下的清晰度 | 矢量是否按固有尺寸光栅化（而非显示时重绘），需两版并排对比观感 |
| 损坏/截断输入是否崩溃 | 「进程未中止、窗口仍响应」是控制流不变量；单测里「函数返回了 Result 错误」不等于「进程没崩」 |
| 不支持格式的优雅拒绝 | 是否被误当其他格式解码出花屏，只能看；程序只能断言返回错误 |
| 大图的可感知卡顿与内存量级 | 是否「肉眼可见地卡」、内存峰值是否数量级异常，是体感与量级判断 |

**不纳入人工测试的部分及其理由**：

| 内容 | 理由 | 已有覆盖 |
|:---|:---|:---|
| 像素级精确比对（哈希 / 逐字节 / 逐像素断言） | 程序判定比人眼精确得多，人工抄录反而引入误差 | `tests/golden/` 下 golden 图比对；`tests/integration/itest_png_image.cpp` 断言编码-解码回环后像素值不变；`Image::content_hash` 摘要比对 |
| 格式嗅探与扩展名映射（`detect_format` / `format_from_path` / `format_name`） | 纯函数，输入可穷举，人工执行无增益 | `tests/unit/utest_image_codec.cpp`：`format_names_are_lowercase_and_distinct`、`detect_format_by_magic`、`detect_webp_by_riff_container`、`format_from_path_uses_extension`、`svg_has_no_magic_and_is_resolved_by_extension` |
| 编解码器注册与调度顺序 | 注册表名与派发顺序可断言，无需人眼 | `utest_image_codec.cpp`：`registry_registers_builtin_codecs`、`custom_codec_is_dispatched_by_sniff` |
| 错误码与错误文案的可操作性 | 载体不打印错误详情（只看得到占位），人工无从核对文案 | `utest_image_codec.cpp`：`decode_garbage_returns_error_not_crash`、`decode_missing_file_returns_error`；`tests/integration/itest_image_stb.cpp` 断言各失败输入的错误码；人工侧只判「不崩溃 + 降级」，已由 TC-IMAGE-006 / 007 / 008 覆盖 |
| 异步解码（`decode_async`） | 线程归属与时序不可靠人工观察；且载体未暴露该入口 | `utest_image_codec.cpp`：`decode_async_resolves_to_same_result`（含无线程能力构建的惰性退化分支） |
| 动图帧序列（`decode_animated` / `AnimatedImage`） | 默认构建无动图解码器，且无展示帧序列的载体 | `utest_image_codec.cpp`：`static_image_degrades_to_single_frame_animation` |
| `DecodeOptions` 的限尺寸缩放与预乘 alpha | 载体未暴露参数入口，人工无法设置 | 缩放的视觉后果由 TC-IMAGE-005 / TC-IMAGE-009 间接覆盖；`EncodeOptions` / `DecodeOptions` 字段语义由单测覆盖 |
