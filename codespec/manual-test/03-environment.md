# environment 模块人工测试用例

> **文档状态：临时（随用例集确认后定稿）**
> 本文件与 `01-core.md` 共享字段范式、格式规范与执行记录表格式，仅被测模块不同。
> 本文件按固定格式编写，供程序解析：字段顺序、字段名、值域与分隔符均为约定的一部分，见 §1.5。

## 1 适用范围与约定

### 1.1 被测模块

`include/aurora/environment/` —— Aurora 的**环境层**，共 3 个公共头：`environment.h`、`build_context.h`、`media_query.h`。在实测依赖分层中位于 L1（与 image 同层）：`environment.h` 仅依赖标准库，`build_context.h` 与 `media_query.h` 仅依赖自身与 core 的类型头。对应规格文档 `codespec/specification/07-environment-modifier.md`。

三个头的分工：

| 头 | 内容 |
|:---|:---|
| `environment.h` | `Environment`：沿树向下传播的类型化键值表（`with` / `get` / `set_local` / `set`，最近祖先优先） |
| `build_context.h` | `BuildContext`：只读位置视图（环境指针 + 缩放因子 + 布局尺寸）与 `env_of` 引用读取 |
| `media_query.h` | `MediaQuery` 值类型与 `ScreenOrientation` / `PlatformKind` / `DeviceKind` 枚举 |

本模块的可观测行为不落在像素样式上，而集中在「运行期动态可观测」两类载体：

| 载体 | 内容 |
|:---|:---|
| 窗口树上的注入值表现 | `MediaQueryProvider` 注入的缩放因子在真实窗口中的读数，及其在拖拽缩放、最大化、跨屏 DPI 变化下的稳定性 |
| 进程级端到端行为 | 控制台通道分流、关闭窗口退出码、多实例隔离、构建上下文本机取值 |

### 1.2 执行载体

复用既有 1:1 载体 `examples/demos/demo_env.cpp`（构建目标 `demo_env`），**零新增代码、无需补建**。

载体行为（读源码并实测确认）：窗口程序。经 `examples/demos/demo_common.h` 的 `run_demo` 打开真实平台窗口，逻辑尺寸 520×380，标题 `Environment · Aurora Demo`；控件树自上而下为渐变横幅标题 `Environment`、说明行 `MediaQueryProvider injects scale factor`、以及一个读数控件 EnvReadout——其经 `MediaQueryProvider` 注入 `MediaQuery::of(2.0)`，在白底细边框矩形内绘制 `scale_factor = 2.000000`。窗口可缩放（窗口样式 `resizable` 默认开启）且已启用 DPI 感知。

该载体的构造同时满足下述约束：

| 约束 | 落地方式 |
|:---|:---|
| 复用既有载体 | `examples/demos/demo_env.cpp` 已是本模块 1:1 载体，零新增代码 |
| 不新增公共 API | 只调用既有公共头与 demo 共享基础设施声明 |
| 真实窗口观测 | `run_demo` 打开可缩放原生窗口，支持拖拽缩放、最大化与跨屏拖动 |
| 判定可复现 | 读数文本由注入常量决定，不含随机数与真实时钟；时间戳、线程 id、行号按可变部分处理（见 §1.7） |
| 与单元测试不重叠 | 载体**只演示、不断言**，不输出 PASS/FAIL；判定由人工对照输出完成 |

### 1.3 执行环境

| 项目 | 要求 |
|:---|:---|
| 平台 | Windows 本机（实测环境为 MinGW g++ + Ninja） |
| 构建 | 库已构建；载体为按需目标，不在默认构建内（`AURORA_BUILD_DEMOS=ON` 时由 `cmake/AuroraDemos.cmake` 按 `examples/demos/` 下的文件名逐一生成目标） |
| 终端 | 支持 UTF-8 输出。`run_demo` 在建窗前调用 `init_console()` 设置控制台代码页 |
| 显示 | 至少一块显示器；TC-ENVIRONMENT-004 需两块显示缩放比例不同的显示器，缺失时该例记 SKIP |

不在本模块范围内：X11、Wayland、Wasm、macOS 等后端相关行为；响应式断点（`BreakpointBuilder`）与 `Provider` 注入控件的实现均属 widget 模块。

### 1.4 用例编号规则

格式 `TC-<模块段>-<三位序号>`，自 001 起连续编号。
模块段为**模块目录名的大写形式**（`core` → `CORE`、`i18n` → `I18N`），**不得自创缩写**——目录名含数字时数字原样保留，故正则为 `^TC-[A-Z0-9]+-\d{3}$`。
本模块目录名 `environment`，即 `TC-ENVIRONMENT-001` 起。序号在本模块内唯一且**不复用**；用例被删除后其编号作废，新用例取下一个可用序号。
用例在文档中**按编号升序声明**——该顺序即默认执行顺序，也是依赖列表排序的依据（见 §1.5）。

### 1.5 用例字段清单与格式规范

每条用例由**六个固定字段**组成，排布于同一张 Markdown 表格内。**字段顺序固定、字段名一字不差、每字段独占一行、单元格内不换行**（需要多条内容时用 `<br>` 分隔）：

| 序号 | 字段 | 格式 | 正则约束 | 说明 |
|:--:|:---|:---|:---|:---|
| 1 | 用例编号 | 单行 | `^TC-[A-Z]+-\d{3}$` | 模块内唯一且不复用 |
| 2 | 测试目的 | 单行 | 自由文本 | 一句话，指向**单一**验证目标 |
| 3 | 前置条件 | 单行 | 自由文本 | 只描述**环境状态**；「必须先执行某用例」属依赖用例字段，不在此重复 |
| 4 | 依赖用例 | 单行 | `^无$` 或 `^TC-[A-Z]+-\d{3}(, TC-[A-Z]+-\d{3})*$` | 见下方规范 |
| 5 | 操作步骤 | 条目列表 | 每条目以 `^\d+\. ` 开头，条目间以 `<br>` 分隔 | 自 1 起连续编号 |
| 6 | 预期结果 | 条目列表 | 同操作步骤；编号是步骤号的**子集** | 见 §1.6 |

**依赖用例字段规范（四条硬性要求）：**

1. 无依赖时**必须**写 `无`，不得留空、不得写 `-`、`N/A`、`none` 等变体。
2. 有依赖时写**用例编号全称**（含模块段），不写省略形式；跨模块依赖同样写全称。
3. 多项依赖以**半角逗号加一个空格**（`, `）分隔；逗号前后不得出现空格以外的字符。
4. 多项依赖的**排列顺序即依赖先后**——先决者在前。因用例按编号升序声明，等价于按被依赖用例的**编号升序**排列。

**模块级约定**：本模块载体的构建步骤统一置于 `TC-ENVIRONMENT-001` 的步骤 1；其余用例不在步骤中重复构建，而是通过依赖用例字段间接依赖其产出的已构建载体。

**为什么必须统一格式**：本文件后续将由程序解析（生成依赖拓扑、按步骤号统计失败点、汇总通过率）。上述约定使每个字段可用**单条正则**校验，无需自然语言推断。

### 1.6 操作步骤与预期结果编号规则

**预期结果与操作步骤同号一一对应**：`预期结果 N` 即「步骤 N 的对应结果」。

1. 预期结果的序号**等于**其对应步骤的序号，两者严格相等——不得因省略而重排、压缩或重新连续编号。
2. 纯执行步骤**不产生预期结果**，其序号在预期结果列表中直接跳过。
3. 故预期结果的序号**不要求连续**，条数也无需等于步骤数。
4. 步骤列表中，纯执行步骤在文本末尾标注「（纯执行，无预期结果）」，供与预期结果列表逐号对照。

示例：某用例有步骤 1、2、3、4，其中步骤 3 为纯执行步骤，则该用例的预期结果共 3 条，编号为 1、2、4。

**该规则解决的问题**：执行者按步骤顺序推进时，编号本身即是映射关系，无需自行推断「这条预期结果对应哪一步」；执行记录可借步骤号精确落到失败点。

### 1.7 判定与记录

| 结果 | 含义 |
|:---|:---|
| PASS | 全部非空预期结果均满足 |
| FAIL | 任一非空预期结果不满足；须在记录表登记该预期结果对应的**步骤号**、实际现象与缺陷编号 |
| BLOCKED | 前置条件无法满足（如载体构建失败），未开始执行 |
| SKIP | 主动判定不适用于本环境（如 TC-ENVIRONMENT-004 缺少不同缩放比例的显示器） |

输出中含**时间戳、线程 id、行号**的字段属可变部分，判定时只核对格式与是否出现，不比对具体值。

**执行记录表格式**（列顺序固定）：

| 列 | 格式 | 允许值 / 正则 |
|:---|:---|:---|
| 用例编号 | 单行 | 与 §2 用例编号一致 |
| 执行日期 | 单行 | `^\d{4}-\d{2}-\d{2}$` |
| 执行人 | 单行 | 自由文本 |
| 结果 | 单行 | `PASS` / `FAIL` / `BLOCKED` / `SKIP` |
| 失败步骤号 | 单行 | 留空（未失败或未执行），或 `^\d+(, \d+)*$`（多个以半角逗号加一个空格分隔） |
| 实际现象 | 单行 | 自由文本 |
| 缺陷编号 | 单行 | 留空或缺陷单号 |
| 备注 | 单行 | 自由文本 |

未执行的取值一律**留空单元格**，不写 `-`、`TBD`、`N/A` 等占位符。

### 1.8 覆盖取舍

本模块按「人工判定是否优于程序判定」取舍，不追求对 3 个头的全覆盖。

**纳入人工测试的子域**（人工能判得比程序准）：

| 子域 | 人工判定优于程序判定的原因 |
|:---|:---|
| 注入值在真实输入下的稳定性 | 人手拖拽、最大化、跨屏拖动产生的连续重排与重绘正确性（残影、错位、闪退）需真实交互时序，程序难以等价模拟 |
| 自动注入与手动 Provider 的覆盖关系 | 「最近祖先优先」在真实窗口树上的可见表现（读数不随窗口尺寸 / DPI 变化）需跨帧并列观察 |
| 多实例隔离 | 注入链按窗口（每棵树）一份、非进程级单例的语义，需两个真实进程并排对照 |
| 控制台通道与退出 | stdout / stderr 分流与关闭窗口退出码属进程级端到端行为，单测无法覆盖窗口关闭路径 |
| 构建上下文本机取值 | 后端开关与 feature 宏的取值需与本机构建、运行表现互证，属环境一致性核对 |

**不纳入人工测试的头及理由**：

| 头 / 子域 | 理由 | 已有覆盖 |
|:---|:---|:---|
| `environment.h`（`with` / `get` / `set_local` / `set` 链式作用域、最近祖先优先、类型键互异） | 纯值逻辑，输入输出可用断言穷举，人工执行无增益 | `tests/unit/utest_environment.cpp` |
| `build_context.h`（`environment<T>()` 查找、`env_of` 引用读取与缺值死亡路径） | 纯查找逻辑；死亡行为由测试框架断言，人工切换构建成本高于价值 | `tests/unit/utest_build_context.cpp` |
| `media_query.h` 纯值语义（默认实例、`of(scale)` 便捷构造、`of(ctx)` 无 Provider 降级） | 纯值逻辑与保守降级取值，断言更精确 | `tests/unit/utest_media_query.cpp` |
| `media_query.h` 的 `resolve_breakpoint` 阈值边界（默认 600 / 840，左闭右开）与 `BreakpointBuilder` 档位切换 | 阈值函数为纯函数；断点控件属 widget 模块（`include/aurora/widget/breakpoint_builder.h`），其人工验证归入 widget 模块用例 | `tests/unit/utest_media_query.cpp` |
| `media_query.h` 的 `from_surface(Surface)` 字段映射与 Window 根级自动注入 | 需要真实 Surface，字段一致性用断言更精确；人工侧仅核对经手动 Provider 覆盖后的稳定表现（TC-ENVIRONMENT-002 / 003 / 004） | `tests/integration/itest_media_query_auto.cpp` |
| `run_demo` 的无显示后端 PNG 回退路径 | 需「无任何可用显示后端」的专用构建配置才能触发，常规本机环境不可复现 | 暂无（已知覆盖空白：需专用构建配置验证） |
