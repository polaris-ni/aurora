# core 模块人工测试用例

> **文档状态：临时（待确认的示例）**
> 本文件是人工测试用例设计的**首份示例**，用于确认用例字段范式、格式规范与覆盖取舍。
> 确认无误后再按依赖顺序补齐其余模块。
> 按约定，本文件**暂不进入 `AGENTS.md` 的文档导航表，其他文档亦不引用它**；定稿后再决定是否转为常驻文档。
>
> **本文件按固定格式编写，供程序解析**：字段顺序、字段名、值域与分隔符均为约定的一部分，见 §1.5。

## 1 适用范围与约定

### 1.1 被测模块

`core/` —— Aurora 的**基础层**（35 个公共头），在实测依赖分层中位于 L0：其公共头**不依赖任何其他 aurora 模块**，只依赖自身与标准库（该边界由 `tools/check/check_core_layer_boundary.py` 守护）。

`core/` 的可观测行为不落在像素上，而集中在两类载体：

| 载体 | 内容 |
|:---|:---|
| 运行期输出通道 | 日志级别阈值、诊断日志与功能输出的通道分流、诊断降级、错误码解释 |
| 编译期判定 | 平台宏与架构宏的取值 |

### 1.2 执行载体

本模块不通过图形界面观测，使用专用控制台载体 `examples/demos/demo_core.cpp`（构建目标 `demo_core`）。
它是一个**纯控制台程序**：不包含 `examples/demos/demo_common.h`、不创建窗口、不依赖任何 Surface 后端。

之所以需要专用载体：`core/` 的能力在既有的 78 个 demo 中**没有 1:1 对应程序**（其余 demo 均围绕单个控件或渲染特性展开，且需要窗口与后端）。该载体的构造同时满足下述约束：

| 约束 | 落地方式 |
|:---|:---|
| 不新增公共 API | 只调用既有 `aurora/core/*.h` 声明 |
| 不引入 GUI 依赖 | 不链接窗口与后端的使用路径，`main` 中不创建窗口 |
| 判定可复现 | 所有观测量为确定性文本与退出码，不含随机数与真实时钟 |
| 与单元测试不重叠 | 载体**只演示、不断言**，不输出 PASS/FAIL；判定由人工对照输出完成 |

### 1.3 执行环境

| 项目 | 要求 |
|:---|:---|
| 平台 | Windows 本机（实测环境为 MinGW/GCC + Ninja） |
| 构建 | 库与载体均已构建；载体为按需目标，不在默认构建内 |
| 终端 | 支持 UTF-8 输出。载体在 `main` 起始处调用 `au::init_console()` 设置控制台代码页，中文不应乱码 |
| 分离输出 | 诊断日志写 stderr，功能输出写 stdout；需分别重定向后对照 |

不在本模块范围内：X11、Wayland、Wasm、macOS 等后端相关行为（`core/` 不含后端实现）。

### 1.4 用例编号规则

格式 `TC-<模块段>-<三位序号>`，自 001 起连续编号。
模块段为**模块目录名的大写形式**（`core` → `CORE`、`i18n` → `I18N`），**不得自创缩写**——目录名含数字时数字原样保留，故正则为 `^TC-[A-Z0-9]+-\d{3}$`。
本模块目录名 `core`，即 `TC-CORE-001` 起。序号在本模块内唯一且**不复用**；用例被删除后其编号作废，新用例取下一个可用序号。
用例在文档中**按编号升序声明**——该顺序即默认执行顺序，也是依赖列表排序的依据（见 §1.5）。

### 1.5 用例字段清单与格式规范

每条用例由**六个固定字段**组成，排布于同一张 Markdown 表格内。**字段顺序固定、字段名一字不差、每字段独占一行、单元格内不换行**（需要多条内容时用 `<br>` 分隔）：

| 序号 | 字段 | 格式 | 正则约束 | 说明 |
|:--:|:---|:---|:---|:---|
| 1 | 用例编号 | 单行 | `^TC-[A-Z]+-\d{3}$` | 模块内唯一且不复用 |
| 2 | 测试目的 | 单行 | 自由文本 | 一句话，指向**单一**验证目标 |
| 3 | 前置条件 | 单行 | 自由文本 | 只描述**环境状态**；「必须先执行某用例」属依赖用例字段，不在此重复 |
| 4 | 依赖用例 | 单行 | `^无$` 或 `^TC-[A-Z]+-\d{3}(, TC-[A-Z]+-\d{3})*$` | 见下方规范 |
| 5 | 操作步骤 | 条目列表 | 每条目以 `^\d+\. ` 开头，条目间以 `<br>` 分隔 | 自 1 起连续编号 |
| 6 | 预期结果 | 条目列表 | 同操作步骤；编号是步骤号的**子集** | 见 §1.6 |

**依赖用例字段规范（四条硬性要求）：**

1. 无依赖时**必须**写 `无`，不得留空、不得写 `-`、`N/A`、`none` 等变体。
2. 有依赖时写**用例编号全称**（含模块段），不写省略形式；跨模块依赖同样写全称。
3. 多项依赖以**半角逗号加一个空格**（`, `）分隔；逗号前后不得出现空格以外的字符。
4. 多项依赖的**排列顺序即依赖先后**——先决者在前。因用例按编号升序声明，等价于按被依赖用例的**编号升序**排列。

**模块级约定**：本模块载体的构建步骤统一置于 `TC-CORE-001` 的步骤 1；其余用例不在步骤中重复构建，而是通过依赖用例字段间接依赖其产出的已构建载体。

**为什么必须统一格式**：本文件后续将由程序解析（生成依赖拓扑、按步骤号统计失败点、汇总通过率）。上述约定使每个字段可用**单条正则**校验，无需自然语言推断。

### 1.6 操作步骤与预期结果编号规则

**预期结果与操作步骤同号一一对应**：`预期结果 N` 即「步骤 N 的对应结果」。

1. 预期结果的序号**等于**其对应步骤的序号，两者严格相等——不得因省略而重排、压缩或重新连续编号。
2. 纯执行步骤**不产生预期结果**，其序号在预期结果列表中直接跳过。
3. 故预期结果的序号**不要求连续**，条数也无需等于步骤数。
4. 步骤列表中，纯执行步骤在文本末尾标注「（纯执行，无预期结果）」，供与预期结果列表逐号对照。

示例：某用例有步骤 1、2、3、4，其中步骤 3 为纯执行步骤，则该用例的预期结果共 3 条，编号为 1、2、4。

**该规则解决的问题**：执行者按步骤顺序推进时，编号本身即是映射关系，无需自行推断「这条预期结果对应哪一步」；执行记录可借步骤号精确落到失败点。

### 1.7 判定与记录

| 结果 | 含义 |
|:---|:---|
| PASS | 全部非空预期结果均满足 |
| FAIL | 任一非空预期结果不满足；须在记录表登记该预期结果对应的**步骤号**、实际现象与缺陷编号 |
| BLOCKED | 前置条件无法满足（如载体构建失败），未开始执行 |
| SKIP | 主动判定不适用于本环境（如被测平台与用例限定平台不符） |

输出中含**时间戳、线程 id、行号**的字段属可变部分，判定时只核对格式与是否出现，不比对具体值。

**执行记录表格式**（列顺序固定）：

| 列 | 格式 | 允许值 / 正则 |
|:---|:---|:---|
| 用例编号 | 单行 | 与 §2 用例编号一致 |
| 执行日期 | 单行 | `^\d{4}-\d{2}-\d{2}$` |
| 执行人 | 单行 | 自由文本 |
| 结果 | 单行 | `PASS` / `FAIL` / `BLOCKED` / `SKIP` |
| 失败步骤号 | 单行 | 留空（未失败或未执行），或 `^\d+(, \d+)*$`（多个以半角逗号加一个空格分隔） |
| 实际现象 | 单行 | 自由文本 |
| 缺陷编号 | 单行 | 留空或缺陷单号 |
| 备注 | 单行 | 自由文本 |

未执行的取值一律**留空单元格**，不写 `-`、`TBD`、`N/A` 等占位符。

### 1.8 覆盖取舍

本模块按「人工判定是否优于程序判定」取舍，不追求对 35 个头的全覆盖。

**纳入人工测试的子域**（人工能判得比程序准）：

| 子域 | 人工判定优于程序判定的原因 |
|:---|:---|
| 日志通道与格式 | 格式是否可读、是否便于定位（时间戳/级别/分类/位置四要素齐全度）属人因判断 |
| 日志级别阈值 | 阈值语义是否符合直觉、边界是否按声明序截断，需人对照多组取值横向比较 |
| 诊断降级 | 「降级而非中止」是**控制流不变量**：需确认进程确实继续运行，而非仅在单测中返回了对象 |
| 错误码解释 | 解释文本对使用者是否**可操作**（能否据此定位），程序只能判非空 |
| 严格模式 | 同一处降级在两种模式下的行为差异，需并列观察 |
| 平台与架构判定 | 编译期取值与本机构建目标是否一致，属环境核对 |

**不纳入人工测试的头及其理由**：

| 头 | 理由 | 已有覆盖 |
|:---|:---|:---|
| `math.h` `utf8.h` `string_util.h` `time.h` `duration.h` `expected.h` `enums.h` `literals.h` `types.h` | 纯函数与纯类型，输入输出可用断言穷举，人工执行无增益 | `tests/unit/` 下同名 `utest_*` 用例 |
| `color.h` `color_space.h` `transform.h` | 类型与数值换算，程序判定更精确；其视觉表现在 render 模块 | `utest_color` `utest_color_space` `utest_transform` |
| `dimension.h` | 单位换算有唯一解，人工抄录输出反而增加误差 | `utest_dimension` `utest_literals` |
| `thread.h` `thread_pool.h` | 并发时序不确定，人工观察不可复现；需 sanitizer 支撑 | `utest_thread` `utest_thread_pool` |
| `file_watcher.h` | 依赖真实文件系统事件，人工执行需长时等待且易受环境干扰 | `utest_file_watcher` |
| `version.h` | 版本号一致性由门禁比对，人工无必要 | `check_version_consistency` 门禁用例、`utest_version` |
| `aurora_assert.h` | debug/release 差异由构建配置决定，人工切换构建成本高于价值 | `utest_assert` |
| `image.h` `font.h` `native_surface.h` | 类型定义为主，行为在 render 与 window 模块体现 | `utest_image` `utest_font` |
| `event_stream.h` `debug.h` `directionality.h` | 纯类型与枚举，或行为在 widget 模块体现 | `utest_event_stream` `utest_debug` |
| `accessibility.h` `a11y_types.h` `a11y_provider.h` `a11y_text.h` | 真实可测但**需要真实辅助技术客户端**（如 Windows 讲述人、Accessibility Insights）才能验证语义树是否被系统读到；且 `core/` 只提供类型与桥抽象，语义树构建在 widget、桥接在 window，属跨模块场景 | `utest_accessibility` `utest_a11y_*`；人工验证归入 widget 与 window 模块用例 |

## 2 用例清单

### 2.1 平台与架构判定

#### TC-CORE-001 平台与架构宏与本机构建目标一致

| 项目 | 内容 |
|:---|:---|
| 用例编号 | TC-CORE-001 |
| 测试目的 | 确认编译期平台宏与架构宏的取值与本次构建的实际目标一致，且指针宽度与架构自洽 |
| 前置条件 | 位于仓库根目录；`build/` 已完成 CMake 配置；本机工具链可用 |
| 依赖用例 | 无 |
| 操作步骤 | 1. 构建载体：`cmake --build build --target demo_core`（纯执行，无预期结果）<br>2. 运行并分离重定向：`./build/demo_core.exe 1> out.txt 2> err.txt`（纯执行，无预期结果）<br>3. 查看 `out.txt` 中「平台与架构（编译期宏判定）」段的 `平台宏:` 行<br>4. 查看同段的 `架构宏:` 行<br>5. 查看同段的 `指针宽度:` 行<br>6. 核对同段中 `平台宏:` 行与 `架构宏:` 行的行数，确认预处理器分支互斥 |
| 预期结果 | 3. 仅出现一个平台宏名，形如 `平台宏: AURORA_PLATFORM_WINDOWS`，与本次构建平台一致；取值为 `<none>` 则 FAIL<br>4. 仅出现一个架构宏名，形如 `架构宏: AURORA_ARCH_X64`，与本次构建目标一致；取值为 `<none>` 则 FAIL<br>5. 指针宽度与架构自洽：x64 / aarch64 / riscv64 为 `8 字节`，x86 / arm32 为 `4 字节`<br>6. `平台宏:` 与 `架构宏:` 各恰 1 行，不存在两个平台宏或两个架构宏同时成立 |

| 项目 | 内容 |
|:---|:---|
| 用例编号 | TC-CORE-002 |
| 测试目的 | 验证诊断日志的通道归属与统一格式，确保出问题时可按位置与分类定位 |

| 依赖用例 | TC-CORE-001 |

### 2.4 诊断收集与降级
