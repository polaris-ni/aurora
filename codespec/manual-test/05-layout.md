## 1 适用范围与约定

### 1.1 被测模块

`layout/` —— Aurora 的**布局层**（公共头四个：`include/aurora/layout/flex.h`、`include/aurora/layout/flex_layouter.h`、
`include/aurora/layout/layout_box.h`、`include/aurora/layout/layout_engine.h`），在实测依赖分层中位于 L2。

**分层事实（以公共头 include 实测为准）**：`layout`、`render`、`state` 三者**互不依赖、平级**，不存在
「layout → render → state」的链式依赖。本模块因此不设跨模块前置。

`layout/` 的可观测行为不落在自身绘制上：`flex.h` 只声明参数结构，`flex_layouter.h` 只做「测 → 摆」求解，
`layout_engine.h` 只驱动 widget 树两阶段布局并收集 `LayoutBox`。它们的结果**通过 Row / Column / Grid /
Stack / Spacer 等容器控件落到窗口像素上**，故本模块的观测载体是这些容器的 demo，观测对象是它们的几何与体感：

| 观测维度 | 内容 |
|:---|:---|
| 静态几何 | 主轴/交叉轴对齐结果、基线共线、网格行列与间距、溢出裁剪边界 |
| 时域体感 | 连续拖拽（分隔条、窗口边框）过程中是否单调、连续、无抖动/闪烁/残影 |

### 1.3 执行环境

| 项目 | 要求 |
|:---|:---|
| 平台 | Windows 本机（实测环境为 MinGW/GCC + Ninja） |
| 构建 | 库与载体均已构建；demo 为按需目标，不在默认构建内 |
| 窗口 | `WindowOptions::resizable` 默认为 `true`，demo 窗口可直接拖拽边框缩放；Win32 后端在 `WM_SIZE` 时触发同步重渲染，故缩放后布局应当跟随 |
| 尺寸口径 | demo 在 `main` 起始处启用 DPI 感知，文档中「px」均指**逻辑像素**，非物理像素；高分屏下不得以截图物理像素比对 |
| 回退路径 | 无可用后端或建窗失败时，`run_demo` 回退无头渲染并写出 PNG 后直接退出——此时窗口不会停留，相关用例判 **SKIP**（见 §1.7） |
| 关闭方式 | 关闭窗口即结束进程；每个用例开头需重新启动对应 demo |

不在本模块范围内：X11 / Wayland / Wasm / macOS 后端的窗口缩放行为（本模块只核对布局结果是否跟随，
后端差异属 window 模块）。

### 1.4 用例编号规则

格式 `TC-<模块段>-<三位序号>`，自 001 起连续编号。
模块段为**模块目录名的大写形式**（`core` → `CORE`、`i18n` → `I18N`），**不得自创缩写**——目录名含数字时数字原样保留，故正则为 `^TC-[A-Z0-9]+-\d{3}$`。
本模块目录名 `layout`，即 `TC-LAYOUT-001` 起。序号在本模块内唯一且**不复用**；用例被删除后其编号作废，新用例取下一个可用序号。
用例在文档中**按编号升序声明**——该顺序即默认执行顺序，也是依赖列表排序的依据（见 §1.5）。

### 1.5 用例字段清单与格式规范

每条用例由**六个固定字段**组成，排布于同一张 Markdown 表格内。**字段顺序固定、字段名一字不差、每字段独占一行、单元格内不换行**（需要多条内容时用 `<br>` 分隔）：

| 序号 | 字段 | 格式 | 正则约束 | 说明 |
|:--:|:---|:---|:---|:---|
| 1 | 用例编号 | 单行 | `^TC-[A-Z]+-\d{3}$` | 模块内唯一且不复用 |
| 2 | 测试目的 | 单行 | 自由文本 | 一句话，指向**单一**验证目标 |
| 3 | 前置条件 | 单行 | 自由文本 | 只描述**环境状态**；「必须先执行某用例」属依赖用例字段，不在此重复 |
| 4 | 依赖用例 | 单行 | `^无$` 或 `^TC-[A-Z]+-\d{3}(, TC-[A-Z]+-\d{3})*$` | 见下方规范 |
| 5 | 操作步骤 | 条目列表 | 每条目以 `^\d+\. ` 开头，条目间以 `<br>` 分隔 | 自 1 起连续编号 |
| 6 | 预期结果 | 条目列表 | 同操作步骤；编号是步骤号的**子集** | 见 §1.6 |

**依赖用例字段规范（四条硬性要求）：**

1. 无依赖时**必须**写 `无`，不得留空、不得写 `-`、`N/A`、`none` 等变体。
2. 有依赖时写**用例编号全称**（含模块段），不写省略形式；跨模块依赖同样写全称。
3. 多项依赖以**半角逗号加一个空格**（`, `）分隔；逗号前后不得出现空格以外的字符。
4. 多项依赖的**排列顺序即依赖先后**——先决者在前。因用例按编号升序声明，等价于按被依赖用例的**编号升序**排列。

**模块级约定**：本模块载体的构建步骤统一置于 `TC-LAYOUT-001` 的步骤 1；其余用例不在步骤中重复构建，而是通过依赖用例字段间接依赖其产出的已构建载体。

**为什么必须统一格式**：本文件后续将由程序解析（生成依赖拓扑、按步骤号统计失败点、汇总通过率）。上述约定使每个字段可用**单条正则**校验，无需自然语言推断。

### 1.6 操作步骤与预期结果编号规则

**预期结果与操作步骤同号一一对应**：`预期结果 N` 即「步骤 N 的对应结果」。

1. 预期结果的序号**等于**其对应步骤的序号，两者严格相等——不得因省略而重排、压缩或重新连续编号。
2. 纯执行步骤**不产生预期结果**，其序号在预期结果列表中直接跳过。
3. 故预期结果的序号**不要求连续**，条数也无需等于步骤数。
4. 步骤列表中，纯执行步骤在文本末尾标注「（纯执行，无预期结果）」，供与预期结果列表逐号对照。

示例：某用例有步骤 1、2、3、4，其中步骤 3 为纯执行步骤，则该用例的预期结果共 3 条，编号为 1、2、4。

**该规则解决的问题**：执行者按步骤顺序推进时，编号本身即是映射关系，无需自行推断「这条预期结果对应哪一步」；执行记录可借步骤号精确落到失败点。

### 1.7 判定与记录

| 结果 | 含义 |
|:---|:---|
| PASS | 全部非空预期结果均满足 |
| FAIL | 任一非空预期结果不满足；须在记录表登记该预期结果对应的**步骤号**、实际现象与缺陷编号 |
| BLOCKED | 前置条件无法满足（如载体构建失败），未开始执行 |
| SKIP | 主动判定不适用于本环境（如建窗失败回退无头渲染、无法拖拽的远程/虚拟桌面会话） |

判定注意事项：

- 几何类判定看**相对关系**（对齐、等距、贴边、不重叠），不以截图像素值逐点比对；尺寸口径为逻辑像素（见 §1.3）。
- 「无抖动 / 无闪烁 / 无残影」属时域观感，判据为**连续帧内是否出现方向回跳、数值突跳或旧几何残留**；偶发单帧撕裂（非重复出现）不判 FAIL，需在备注中记录频率。
- demo 内的说明性文案若与实现不一致（如 `demo_overflow` 中 Scroll 的「reserved」字样），**只记录不判缺陷**，缺陷应开在实现侧并在备注注明。

**执行记录表格式**（列顺序固定）：

| 列 | 格式 | 允许值 / 正则 |
|:---|:---|:---|
| 用例编号 | 单行 | 与 §2 用例编号一致 |
| 执行日期 | 单行 | `^\d{4}-\d{2}-\d{2}$` |
| 执行人 | 单行 | 自由文本 |
| 结果 | 单行 | `PASS` / `FAIL` / `BLOCKED` / `SKIP` |
| 失败步骤号 | 单行 | 留空（未失败或未执行），或 `^\d+(, \d+)*$`（多个以半角逗号加一个空格分隔） |
| 实际现象 | 单行 | 自由文本 |
| 缺陷编号 | 单行 | 留空或缺陷单号 |
| 备注 | 单行 | 自由文本 |

未执行的取值一律**留空单元格**，不写 `-`、`TBD`、`N/A` 等占位符。

### 1.8 覆盖取舍

本模块按「人工判定是否优于程序判定」取舍，不追求对四个头的全覆盖。

**纳入人工测试的子域**（人工能判得比程序准）：

| 子域 | 人工判定优于程序判定的原因 |
|:---|:---|
| 主轴/交叉轴对齐在极端内容下的观感 | 内容远小于容器时「空白留在哪一侧」「是否居中」是体感判断；程序只能断言坐标相等 |
| 交叉轴基线对齐 | 不同字号的首行基线是否共线、无基线子项是否按合成基线参与，属视觉判断且含人因容错语义 |
| 溢出策略的视觉与交互 | 裁剪边界是否规则、滚动是否连续并在两端夹住，需人眼看连续帧与手感 |
| min/max 约束在连续拖拽中的连续性 | 抖动、跳变、闪烁是**时域观感**，单帧断言无法证伪 |
| 网格行列与间距 | 行列是否等宽、间隙是否一致、行高是否由该行最高项决定，肉眼横向比对更快 |
| 窗口连续缩放时的布局跟随 | 需观察连续帧序列是否残留旧几何、是否出现跳变 |

**不纳入人工测试的子域及其理由**：

| 子域 | 理由 | 已有覆盖 |
|:---|:---|:---|
| `FlexLayouter::layout` 的精确坐标解（给定 `Flex` 配置与 `Constraints`，求各子项 `Rect` 与容器 `Size`） | 输入确定、输出唯一，人眼读像素反而引入误差 | `tests/unit/utest_flex_layouter.cpp`、`tests/unit/utest_flex.cpp` |
| 四种 `FlexDirection` 与 `Flex::rtl` 镜像的几何 | 数值可穷举，人工只能目测「大致翻转」 | `tests/unit/utest_flex_layouter.cpp`、`tests/unit/utest_flex.cpp` |
| `MainAxisSize::Min` / `Max`、`Flex::gap`、flex 权重的空间分配数值 | 纯分配算术，程序断言更精确 | `tests/unit/utest_flex.cpp`、`tests/unit/utest_flex_layouter.cpp` |
| `LayoutBox` 树与 `LayoutEngine::build_box` / `layout_to_box` 收集的约束与几何 | 树结构与字段值属数据结构断言，不可目视 | `tests/unit/utest_layout_box.cpp`、`tests/unit/utest_layout_engine.cpp` |
| 布局查询（几何/命中查询接口） | 返回值需精确比对，人工无增益 | `tests/unit/utest_layout_query.cpp` |
| 百分比与 fill 尺寸意图的像素解（`include/aurora/core/dimension.h` 的 `percent()` / `fill()` 按父级解析） | **无可视化载体**：`examples/` 下没有任何 demo 使用百分比尺寸，人工只能复述同一组数字；其「容器缩放时的连续性」须待补建载体后再纳入 | `tests/integration/itest_percent_layout.cpp` |
| RelayoutBoundary 截断（`mark_needs_layout` 是否冒泡置根脏） | 判据是 `on_layout` 调用次数，肉眼不可见 | `tests/integration/itest_relayout_boundary.cpp` |
| `OverflowStrategy` 枚举的 JSON 往返与未知值回退 | 序列化语义，与视觉无关 | `tests/integration/itest_overflow_strategy.cpp` |

**取舍说明**：需求中提到的「min/max 约束与百分比在容器缩放时的连续性」一分为二——
min/max 连续性有现成载体（`demo_splitter` 的 `set_min_sizes` + 可拖拽分隔条），纳入 TC-LAYOUT-009；
百分比连续性因无载体**不纳入**，理由见上表，待补建可视化载体后再行增补（补建须先报告并走格式化、静态检查、构建运行三步）。
