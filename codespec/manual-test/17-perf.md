# perf 模块人工测试用例

> **文档状态：临时**
> 本文件按固定格式编写，供程序解析：字段顺序、字段名、值域与分隔符均为约定的一部分，见 §1.5。
> 格式规范与首份示例见 `codespec/manual-test/01-core.md`。

## 1 适用范围与约定

### 1.1 被测模块

`perf/` —— 性能观测层（8 个公共头），在实测依赖分层中位于 L6。

| 头 | 职责 |
|:---|:---|
| `stopwatch.h` | 计时 |
| `counters.h` | 计数类指标 |
| `profiler.h` | 取样式剖析 |
| `perf_log.h` | 性能日志 |
| `perf_session.h` | 会话：多轮采样与汇总 |
| `trace_writer.h` | 轨迹写出 |
| `scroll_bench.h` | 滚动基准场景 |

本模块的人工增益集中在**数量级与相对关系的合理性**：基准能给出精确到微秒的数值，而人来判断的是「这个数值关系是否符合架构预期」——例如「局部脏区重绘比全量重绘快两个数量级」是不是真的成立。这类判断程序做不了，因为它需要知道**预期应该是什么**。

### 1.2 执行载体

复用既有基准程序，不新增载体：

| 载体 | 构建目标 | 用途 |
|:---|:---|:---|
| `tools/bench/bench_render.cpp` | `bench_render` | 13 类绘制场景 × 3 档逻辑尺寸 × 3 档缩放的逐帧耗时 |
| `tools/bench/bench_scroll.cpp` | `bench_scroll` | 滚动帧时间分布（p99 / 最差 / 抖动 / 长任务） |
| `tools/bench/bench_idle_cpu.cpp` | `bench_idle_cpu` | 空闲状态下的 CPU 占用 |
| `tools/bench/bench_win32_present.cpp` | `bench_win32_present` | Win32 上屏路径耗时 |
| `tools/bench/bench_gpu.cpp` | `bench_gpu` | GPU 后端基准（本机构建未启用该后端） |
| `tools/check/perf_gates.json` | —（数据文件） | 门槛定义，人工判定的对照基准 |

`bench_render` 的输出为 Markdown 表格并经 `AURORA_LOG_RAW` 写到 **stdout**，因此可直接重定向为文件留档与逐行比较。

**关于门槛的分工**：`tools/check/perf_gates.json` 中共有 G-1 至 G-8 八项门槛，其中时间类（G-1 至 G-4）**不进 CI**，仅用于本地趋势对照（该文件自身声明了这一点）；计数类（G-5 至 G-8）已锁定在 CTest 的滚动回归段。因此本模块的人工用例覆盖时间类门槛的对照，计数类只做「是否已由自动化守护」的确认。

### 1.3 执行环境

| 项目 | 要求 |
|:---|:---|
| 平台 | Windows 本机（实测环境为 MinGW/GCC + Ninja） |
| 构建 | 五个基准目标已构建 |
| 终端 | 支持 UTF-8 输出 |
| 负载 | **判定前须关闭占用 CPU 的后台任务**（浏览器、编译、杀毒扫描等）；时间类指标对机器负载敏感 |
| 电源 | 建议接入电源并设为高性能模式；笔记本省电模式会显著抬高帧时间 |
| 记录 | 建议把 stdout 重定向留档，便于两轮对照 |

本机启用 `AURORA_BACKEND_WIN32` 与 `AURORA_BACKEND_HEADLESS`，未启用 GLFW / D3D11 / wgpu，故 `bench_gpu` 的 GPU 路径在本机不可执行，相关判定记 `SKIP`。

### 1.4 用例编号规则

格式 `TC-<模块段>-<三位序号>`，自 001 起连续编号。
模块段为**模块目录名的大写形式**（`core` → `CORE`、`i18n` → `I18N`），**不得自创缩写**——目录名含数字时数字原样保留，故正则为 `^TC-[A-Z0-9]+-\d{3}$`。
本模块目录名 `perf`，即 `TC-PERF-001` 起。序号在本模块内唯一且**不复用**；用例被删除后其编号作废，新用例取下一个可用序号。
用例在文档中**按编号升序声明**——该顺序即默认执行顺序，也是依赖列表排序的依据（见 §1.5）。

### 1.5 用例字段清单与格式规范

每条用例由**六个固定字段**组成，排布于同一张 Markdown 表格内。**字段顺序固定、字段名一字不差、每字段独占一行、单元格内不换行**（需要多条内容时用 `<br>` 分隔）：

| 序号 | 字段 | 格式 | 正则约束 | 说明 |
|:--:|:---|:---|:---|:---|
| 1 | 用例编号 | 单行 | `^TC-[A-Z0-9]+-\d{3}$` | 模块内唯一且不复用 |
| 2 | 测试目的 | 单行 | 自由文本 | 一句话，指向**单一**验证目标 |
| 3 | 前置条件 | 单行 | 自由文本 | 只描述**环境状态**；「必须先执行某用例」属依赖用例字段，不在此重复 |
| 4 | 依赖用例 | 单行 | `^无$` 或 `^TC-[A-Z0-9]+-\d{3}(, TC-[A-Z0-9]+-\d{3})*$` | 见下方规范 |
| 5 | 操作步骤 | 条目列表 | 每条目以 `^\d+\. ` 开头，条目间以 `<br>` 分隔 | 自 1 起连续编号 |
| 6 | 预期结果 | 条目列表 | 同操作步骤；编号是步骤号的**子集** | 见 §1.6 |

**依赖用例字段规范（四条硬性要求）：**

1. 无依赖时**必须**写 `无`，不得留空、不得写 `-`、`N/A`、`none` 等变体。
2. 有依赖时写**用例编号全称**（含模块段），不写省略形式；跨模块依赖同样写全称。
3. 多项依赖以**半角逗号加一个空格**（`, `）分隔；逗号前后不得出现空格以外的字符。
4. 多项依赖的**排列顺序即依赖先后**——先决者在前。因用例按编号升序声明，等价于按被依赖用例的**编号升序**排列。

**模块级约定**：本模块的基准程序属默认构建产物，其构建步骤仍统一置于 `TC-PERF-001` 的步骤 1（与其他模块保持同一形式）；其余用例不在步骤中重复构建，而是通过依赖用例字段间接依赖其产出的已构建基准。

**为什么必须统一格式**：本文件后续将由程序解析（生成依赖拓扑、按步骤号统计失败点、汇总通过率）。上述约定使每个字段可用**单条正则**校验，无需自然语言推断。

### 1.6 操作步骤与预期结果编号规则

**预期结果与操作步骤同号一一对应**：`预期结果 N` 即「步骤 N 的对应结果」。

1. 预期结果的序号**等于**其对应步骤的序号，两者严格相等——不得因省略而重排、压缩或重新连续编号。
2. 纯执行步骤**不产生预期结果**，其序号在预期结果列表中直接跳过。
3. 故预期结果的序号**不要求连续**，条数也无需等于步骤数。
4. 步骤列表中，纯执行步骤在文本末尾标注「（纯执行，无预期结果）」，供与预期结果列表逐号对照。

示例：某用例有步骤 1、2、3、4，其中步骤 3 为纯执行步骤，则该用例的预期结果共 3 条，编号为 1、2、4。

**该规则解决的问题**：执行者按步骤顺序推进时，编号本身即是映射关系，无需自行推断「这条预期结果对应哪一步」；执行记录可借步骤号精确落到失败点。

### 1.7 判定与记录

| 结果 | 含义 |
|:---|:---|
| PASS | 全部非空预期结果均满足 |
| FAIL | 任一非空预期结果不满足；须在记录表登记该预期结果对应的**步骤号**、实际现象与缺陷编号 |
| BLOCKED | 前置条件无法满足（如载体构建失败），未开始执行 |
| SKIP | 主动判定不适用于本环境（如被测平台与用例限定平台不符） |

输出中含**时间戳、线程 id、行号**的字段属可变部分，判定时只核对格式与是否出现，不比对具体值。

**性能类用例的判定附加约定**：

1. 判定对象是**数量级与相对关系**，不是绝对数值。故预期结果中给出的实测值仅作参照，判 FAIL 的门槛是数量级偏离（如预期快两个数量级而实测仅快三成）。
2. 数值随机器负载波动属正常；若某次运行明显偏离，应在**关闭后台负载后重跑一次**再判定，不得据单次结果直接判 FAIL。
3. 每轮判定都应在记录表的「实际现象」列写下当轮的实测数值，便于跨轮比较。

**执行记录表格式**（列顺序固定）：

| 列 | 格式 | 允许值 / 正则 |
|:---|:---|:---|
| 用例编号 | 单行 | 与 §2 用例编号一致 |
| 执行日期 | 单行 | `^\d{4}-\d{2}-\d{2}$` |
| 执行人 | 单行 | 自由文本 |
| 结果 | 单行 | `PASS` / `FAIL` / `BLOCKED` / `SKIP` |
| 失败步骤号 | 单行 | 留空（未失败或未执行），或 `^\d+(, \d+)*$`（多个以半角逗号加一个空格分隔） |
| 实际现象 | 单行 | 自由文本 |
| 缺陷编号 | 单行 | 留空或缺陷单号 |
| 备注 | 单行 | 自由文本 |

未执行的取值一律**留空单元格**，不写 `-`、`TBD`、`N/A` 等占位符。

### 1.8 覆盖取舍

本模块按「人工判定是否优于程序判定」取舍，不追求对 8 个头的全覆盖。

**纳入人工测试的子域**：

| 子域 | 人工判定优于程序判定的原因 |
|:---|:---|
| 局部重绘相对全量重绘的收益 | 判断的是「差距是否达到架构预期的量级」，需要预期知识 |
| 缩放因子对耗时的影响 | 判断的是「增长是否与像素数增长相称」，属数量级合理性 |
| 各绘制原语的相对开销 | 判断的是「哪些原语贵、贵多少」的排序是否符合直觉 |
| 滚动帧时间分布 | p99 与最差帧是否落在门槛内、抖动是否可接受 |
| 空闲 CPU 占用 | 「不动时是否安静」是体感指标，程序能测数值但判定标准来自使用预期 |
| 门槛分工的确认 | 确认时间类门槛不进 CI、计数类已由自动化守护，避免重复投入 |

**不纳入人工测试的头及其理由**：

| 头 | 理由 | 已有覆盖 |
|:---|:---|:---|
| `stopwatch.h` | 计时原语为薄封装，取值精度由系统时钟决定 | `utest_stopwatch` |
| `counters.h` | 计数指标为确定性累加 | `utest_counters` |
| `profiler.h` | 取样式剖析的栈维护为确定性逻辑 | `utest_profiler` |
| `perf_log.h` | 性能日志的格式化与写出为确定性 | `utest_perf_log` |
| `perf_session.h` | 会话的多轮汇总与统计为确定性数值处理；其**结果解读**由 TC-PERF-002 至 TC-PERF-005 覆盖 | `utest_perf_session` |
| `trace_writer.h` | 轨迹序列化为确定性 | `utest_trace_writer` |
| `scroll_bench.h` | 滚动基准场景的构造为确定性；其**指标与门槛对照**由 TC-PERF-005 覆盖 | `utest_scroll_bench` `utest_scroll` |
| `tools/bench/*` 的计数类门槛（G-5 至 G-8） | 已由 CTest 的滚动回归段守护（需 `PROFILING=ON`），人工重复执行无增益 | `utest_scroll` 滚动回归段 |

### 2.2 绘制开销的数量级关系

#### TC-PERF-002 局部脏区重绘显著快于全量重绘

| 项目 | 内容 |
|:---|:---|
| 用例编号 | TC-PERF-002 |
| 测试目的 | 验证「只重绘变化的小块」相对「整树全量重绘」的收益达到架构预期的量级——这是整套脏区机制的立命之本 |
| 前置条件 | 基准 `bench_render` 已构建成功；后台无占用 CPU 的任务；已留存 `render_baseline.md` |
| 依赖用例 | TC-PERF-001 |
| 操作步骤 | 1. 运行 `./build/bench_render.exe 1> render_baseline.md`（纯执行，无预期结果）<br>2. 在表格中定位逻辑尺寸 `1280x720`、缩放 `1.0` 下的 `tree_full_redraw` 行，读取其 `ms/frame`<br>3. 在同一分组下定位 `tree_dirty_one_chip` 行，读取其 `ms/frame`<br>4. 计算两者比值<br>5. 在缩放 `2.0` 的分组下重复步骤 2 至 4 |
| 预期结果 | 2. `tree_full_redraw` 的耗时为个位数毫秒（实测参照值 8.509 ms）<br>3. `tree_dirty_one_chip` 的耗时显著更低（实测参照值 0.047 ms）<br>4. 比值达到**两个数量级**（实测约 180 倍）。若比值低于 10 倍，说明脏区裁剪未真正生效，即 FAIL<br>5. 在更高缩放下该比值仍保持同一量级（实测约 200 倍），不出现「缩放一提高脏区优势就消失」的情形 |

#### TC-PERF-003 渲染耗时随像素数增长而相称增长

| 项目 | 内容 |
|:---|:---|
| 用例编号 | TC-PERF-003 |
| 测试目的 | 验证耗时增长与物理像素数的增长相称，未出现超线性的劣化（超线性意味着存在随尺寸放大的隐藏开销） |
| 前置条件 | 基准 `bench_render` 已构建成功；后台无占用 CPU 的任务 |
| 依赖用例 | TC-PERF-001 |
| 操作步骤 | 1. 运行 `./build/bench_render.exe 1> render_baseline.md`（纯执行，无预期结果）<br>2. 取 `fill_alpha_full` 场景，分别读取缩放 `1.0`（物理 1280x720）与 `1.5`（物理 1920x1080）两行的 `ms/frame`（纯执行，无预期结果）<br>3. 计算耗时比值，并与物理像素数比值（1.5 的平方，即 2.25）对照<br>4. 取 `tree_full_redraw` 场景，重复步骤 2 与步骤 3（纯执行，无预期结果）<br>5. 比较两者的增长倍数 |
| 预期结果 | 3. 两个缩放档的耗时比值约为 2.25 的量级（实测 `fill_alpha_full` 由 1.566 增至 3.790，约 2.4 倍）；若超过 4 倍，说明存在超线性劣化，即 FAIL<br>5. `tree_full_redraw` 的增长倍数与步骤 3 的量级相当（实测约 1.4 倍，略低于像素增长，属正常波动范围），不存在某一场景随缩放急剧恶化 |

#### TC-PERF-004 各绘制原语的相对开销顺序合理

| 项目 | 内容 |
|:---|:---|
| 用例编号 | TC-PERF-004 |
| 测试目的 | 验证绘制原语之间的开销排序符合算法预期，可用于指导优化优先级 |
| 前置条件 | 基准 `bench_render` 已构建成功；后台无占用 CPU 的任务 |
| 依赖用例 | TC-PERF-001 |
| 操作步骤 | 1. 运行 `./build/bench_render.exe 1> render_baseline.md`（纯执行，无预期结果）<br>2. 在逻辑尺寸 `1280x720`、缩放 `1.0` 的分组下，读取 `fill_opaque_full`（不透明填充）与 `fill_alpha_full`（半透明填充）两行的耗时（纯执行，无预期结果）<br>3. 比较两者的量级差<br>4. 该分组下读取 `hit_test_x1000`（命中测试 1000 次）的耗时（纯执行，无预期结果）<br>5. 比较命中测试与单次全屏填充的耗时 |
| 预期结果 | 3. 半透明填充明显慢于不透明填充（实测 1.566 ms 对 0.123 ms，约 13 倍）——因为半透明需要逐像素混合，此差异属预期<br>5. 命中测试 1000 次的耗时**低于**一次全屏不透明填充（实测 0.054 ms 对 0.123 ms 的同一量级），说明命中测试开销极低、不构成滚动瓶颈；若命中测试成为最慢项之一，即 FAIL |

### 2.3 滚动与空闲

#### TC-PERF-005 滚动帧时间分布落在门槛内

| 项目 | 内容 |
|:---|:---|
| 用例编号 | TC-PERF-005 |
| 测试目的 | 验证滚动场景的 p99、最差帧与抖动三项时间类指标均可与门槛逐项对照 |
| 前置条件 | 基准 `bench_scroll` 已构建成功；后台无占用 CPU 的任务；已读 `tools/check/perf_gates.json` 的门槛定义 |
| 依赖用例 | TC-PERF-001 |
| 操作步骤 | 1. 运行 `./build/bench_scroll.exe 1> scroll_baseline.txt 2> err.txt`（纯执行，无预期结果）<br>2. 记录退出码并在输出中定位三项指标：p99 帧时间、最差帧时间、抖动<br>3. 从 `tools/check/perf_gates.json` 取出 G-1（p99 门槛）、G-2（最差帧门槛）、G-3（抖动门槛）三项阈值（纯执行，无预期结果）<br>4. 把三项实测值与三项阈值逐项对照<br>5. 查找输出中的长任务计数并对照 G-4 阈值 |
